# CODESYS-Based Controllers, Open-Source / Soft-PLC Runtimes, and Linux-Based Industrial Controllers as PEAT Module Candidates

Research date: 2026-10-31. Scope: CODESYS V3 (generic), WAGO PFC/CC100/Edge, Beckhoff TwinCAT 3, Phoenix Contact PLCnext, B&R Automation Studio/ARsim, OpenPLC v3 (vs. existing v4 module), Revolution Pi, Inductive Automation Ignition, open-source SCADA (Rapid SCADA, FUXA, ScadaBR), and OPC UA as a cross-vendor identity source. Per the PEAT maintainer's clarification received mid-task, each candidate below states explicitly whether PARSE and SCAN are achievable without hardware; pull/push are treated as secondary.

Method note: ~45 web searches/fetches plus local inspection of the PEAT repo (`peat/modules/openplc/openplcv4.py`, `.github/workflows/tests-container.yml`, `tests/modules/openplc/data_files/Relay_Blink_PLC.zip`). The per-turn web-search budget was exhausted near the end, so a handful of items (PLCnext REST API docs, Beckhoff/B&R/Ignition CISA advisories, Shodan CODESYS counts, CODESYS store product pages) could not be re-queried and are listed as gaps rather than guessed.

## Key Question 1: Which runtimes can run headless in Docker on a Linux CI runner for free, with no (or an acceptable) time bomb, and what network services do they expose for scan/pull?

### Takeaway
Four candidates have a free, network-reachable soft runtime that can run on a Linux CI host: OpenPLC v3 (Docker, GPL, no time limit), CODESYS Virtual Control / Control for Linux SL (official container image, free demo mode that stops after 2 hours but restarts cleanly; download requires a free CODESYS Store account), Ignition (official Docker image, unlicensed "trial mode" runs 2 hours and can be reset an unlimited number of times), and any OPC UA server (e.g. the LGPL asyncua server, or Ignition/FUXA). Phoenix Contact's Virtual PLCnext Control is on Docker Hub but requires a CodeMeter network license server plus a PREEMPT_RT kernel/podman/AppArmor host; Beckhoff's TwinCAT runtime is Windows- or Beckhoff-hardware-bound (7-day renewable trial); B&R ARsim is Windows-only with ambiguous licensing; WAGO and Revolution Pi have no emulator.

### Cited Findings

**CODESYS (Virtual Control SL / Control for Linux SL)**
- The CODESYS Virtual Control SL datasheet (creation date 2026-09-24) lists "Demo-/Test-Mode: yes, 2 hours", delivery as a "CODESYS package, which contains the runtime system as a Debian package and as a container image" based on the OSADL base image, CPU architectures x86_64/ARM/ARM64, "Support of a container engine required (Docker/Podman)", kernel >= 6.1 (Debian 12 OSADL image), "No support for WSL", requires CODESYS Development System V3.5.20.10+ and Virtual Control SL V4.12.0.0+, and "Note: Without a license, each controller runs in demo mode for two hours." Licensing is "application-based network licensing" via CODESYS LicenseServer for Linux SL. — [CODESYS Virtual Control SL datasheet (PDF)](https://us.store.codesys.com/media/n98_media_assets/files/000138/2/CODESYS%20Virtual%20Control%20SL_en.pdf)
- CODESYS online help: Virtual Control SL "virtual runtimes are built on Docker or Podman container technology"; a "Runtime Deploy tool" transfers images to targets and manages instances. — [CODESYS Help: Virtual Control SL overview](https://content.helpme-codesys.com/en/CODESYS%20Control/_rtsl_virtual_control_sl_overview.html)
- Intel ECI documentation: "The CODESYS Linux runtime is free to use without a license, however it will automatically stop execution after two hours"; restart with `sudo systemctl restart codesyscontrol`; without a license the OPC UA client stops after 30 minutes; the CODESYS Store download "requires an account: You need to create a free account for the download to be available"; the IDE is Windows-only. — [Intel ECI: CODESYS](https://eci.intel.com/docs/3.1/components/codesys.html)
- Intel ECI container guidance: only CODESYS Control for Linux SL 3.5.16.20-and-older or 4.5.0.0-and-newer work correctly in containers (4.0–4.4 do not); images (`codesys-control`, `codesys-control-apploader`) are built from the CODESYS package with a build script, then `docker load`ed; there is no official Docker Hub image. — [Intel ECI: CODESYS runtime microservice](https://eci.intel.com/docs/3.0/components/microservices/codesys-runtime.html)
- CODESYS Forge users report the Raspberry Pi runtime: "after 2h the plc quits you need to restart it or reboot it" and the log message "no runtime license - running in demo mode(~2 hours)". — [Forge thread 571147cfab](https://forge.codesys.com/forge/talk/Runtime/thread/571147cfab); [Forge thread 6d29b6b4de](https://forge.codesys.com/forge/talk/Runtime/thread/6d29b6b4de/?limit=25)
- Network services: CODESYS V3 protocol runs over TCP 11740–11743 and UDP 1740–1743. — [Microsoft Security Blog, Aug 2023](https://www.microsoft.com/en-us/security/blog/2023/08/10/multiple-high-severity-vulnerabilities-in-codesys-v3-sdk-could-lead-to-rce-or-dos/); Forge users citing the manual confirm the same ranges, and one Wireshark analysis describes UDP 1740 as broadcast discovery, 1741 handshake/responses, 1742/1743 fallbacks (user-reported, not official). — [Forge thread d2afaab5d2](https://forge.codesys.com/forge/talk/Engineering/thread/d2afaab5d2); [Forge thread b9b88de1f4](https://forge.codesys.com/forge/talk/Engineering/thread/b9b88de1f4/)
- Kaspersky's 2019 talk shows a CODESYS runtime started with `-vvvvvvv` printing unauthenticated identity to its console: "CODESYS Control V3.5.12.0 for ARM - build Dec 18 2017 / type:4102 id:0x00000010 name:CODESYS Control for Raspberry Pi SL / vendor: 3S - Smart Software Solutions GmbH" (device type, target ID, name, vendor are the fields the runtime knows about itself). — [Kaspersky ICS Conference 2019, "The fall of CODESYS" (PDF)](https://go.kaspersky.com/rs/802-IJN-240/images/06-Alexander-Nochvay-The-fall-of-CODESYS.-Researching-security-of-the-framework-for-PLC-control.pdf)

**OpenPLC v3**
- Repo: GPL-3.0; "has reached End of Life and is no longer maintained", archived read-only; ~1.6k stars, 615 forks; install options `./install.sh linux|win|rpi|docker|custom`; Docker: `docker build -t openplc:v3 .` then run with `-p 8080:8080`. — [thiagoralves/OpenPLC_v3](https://github.com/thiagoralves/OpenPLC_v3)
- `webserver.py`: Flask app; `app.run(debug=False, host='0.0.0.0', threaded=True, port=8080)`; a second Flask app `app_restapi` on port 8443 with a generated self-signed cert registers blueprint `restapi_bp` at `/api` with GET actions `start-plc`, `stop-plc`, `runtime-logs`, `compilation-status`, `status`, `ping` and POST `upload-file` (32 MB limit); authentication via `flask_login`, password compared in plaintext (`if (row[1] == password)`), 5-minute permanent sessions, secret key regenerated each start; SQLite `openplc.db` tables `Users`, `Programs`, `Settings` (keys `Modbus_port`, `Dnp3_port`, `Enip_port`, `snap7`, `Start_run_mode`, ...), `Slave_dev`; routes `/login`, `/start_plc`, `/stop_plc`, `/runtime_logs`, `/dashboard`, `/programs`, `/upload-program` (multipart `file`, saved to `st_files/`), `/compile-program?file=`, `/compilation-logs`, `/modbus`, `/monitoring`, `/hardware`, `/users`, `/settings`, `/logout`. — [webserver.py (raw)](https://raw.githubusercontent.com/thiagoralves/OpenPLC_v3/master/webserver/webserver.py)
- Default credentials `openplc`/`openplc` on port 8080 (third-party guide; confirmed working in a HTB writeup). — [plcprogramming.io troubleshooting](https://plcprogramming.io/openplc/troubleshooting); [CSIRT-MU HTB writeup](https://writeups.csirt.muni.cz/content/htb/Machines/WifineticTwo/writeup/)
- Hilscher publishes a prebuilt Docker image of OpenPLC v3 for netPI (ARM). — [HilscherAutomation/netPI-openplc](https://github.com/HilscherAutomation/netPI-openplc)
- PEAT's existing v4 CI uses `ghcr.io/autonomy-logic/openplc-runtime:latest` and asserts an `openplc_api` service on 8443 (local: `.github/workflows/tests-container.yml`, `tests/modules/openplc/test_openplcv4_container.py`).

- Community image `kcollins/ignition` supports `IGNITION_EDITION=maker` (needs license key + activation token) and restores a `.gwbk` mounted at `/restore.gwbk` on first start. — [Docker Hub: kcollins/ignition](https://hub.docker.com/community/images/kcollins/ignition)

**Beckhoff TwinCAT 3**

**OPC UA servers (cross-vendor)**
- asyncua (FreeOpcUa/opcua-asyncio): LGPL-3.0, Python >= 3.10, ~1.5k stars, 2,629 commits; includes a server implementation and the `uadiscover` tool covering `find_servers`, `get_endpoints`, `find_servers_on_network`. — [FreeOpcUa/opcua-asyncio](https://github.com/FreeOpcUa/opcua-asyncio)

### Inferences
- For a GitHub Actions Linux runner, the only runtimes with zero licensing friction are OpenPLC v3 (build from the archived repo's Dockerfile), FUXA/Rapid SCADA, and an asyncua OPC UA server. CODESYS Virtual Control is technically CI-capable (Docker/Podman, x86_64, headless) but the CI job would need to download the CODESYS package with store-account credentials at run time or bake a private image, because the package is distributed under CODESYS's EULA via an account-gated store; the 2-hour demo limit is harmless for a CI job that lasts minutes.
- Ignition's official image plus unlimited trial resets makes it CI-feasible for scan tests (the Gateway web UI is reachable in trial mode); automating "Reset Trial" is not needed for a short CI run.
- Virtual PLCnext Control is not CI-practical without a CodeMeter license server and a PREEMPT_RT host; TwinCAT XAR needs Windows (multi-GB install) or Beckhoff hardware; ARsim needs Windows and possibly a Technology Guard. These can support local developer testing but not hardware-free CI.

### Gaps
- Whether Virtual PLCnext Control runs at all (even briefly) without a CodeMeter license was not stated in any fetched source.
- CODESYS Control Win SL and Control for Raspberry Pi SL store pages returned HTTP 404 on fetch; 2-hour demo behavior for those SKUs rests on Forge user reports and Intel's Linux SL documentation.
- Whether TwinCAT/BSD can be downloaded as a free VM image (and whether a trial runtime license can be activated inside a VM) was not verified (Beckhoff page fetch returned 404; no search budget remained).
- Ignition's HTTP endpoints that reveal version without login were not verified from documentation.

## Key Question 2: Which project formats are plain XML/JSON (TwinCAT, B&R, PLCopen exports, etc.) with public sample projects?

### Takeaway
TwinCAT 3 is the standout: `.TcPOU`/`.TcDUT`/`.TcGVL` are XML, `.plcproj` is MSBuild XML, `.tsproj` is XML, and Beckhoff's own GitHub org publishes dozens of sample repos (many under the Zero-Clause BSD license) that can be used as redistributable fixtures. PLCopen TC6 XML is the common denominator for CODESYS (export), OpenPLC Editor/Beremiz (`plc.xml`, already present in a PEAT fixture) and PLCnext (IEC 61131-10 export). B&R Automation Studio files are reported to be XML/text, but no redistributable public sample project was verified. CODESYS `.project` internals are undocumented; CODESYS provides a native XML `*.export` and PLCopen XML export instead. PLCnext `.pcwex` is a compressed project and `.pcwef` an uncompressed on-disk form; Revolution Pi `config.rsc` is JSON; Ignition `.gwbk` is a ZIP containing an SQLite DB and project folders.

### Cited Findings
- CODESYS export: "There are two ways to do this": a native XML export file (`*.export`) that is "fully compatible with the CODESYS project format" with objects "stored in a machine-parsable XML format", and PLCopen XML (`*.xml`), which "defines a subset of the elements known in CODESYS. 100% compatibility is thus not guaranteed." — [CODESYS Help: Exporting and Importing Projects](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_project_export_import.html)
- TwinCAT 3 file types (third-party tool docs): `.TcPOU` holds PLC code as XML with Declaration and Implementation sections; `.plcproj` is MSBuild-style listing `Compile` items; `.tsproj` is TcSmProject XML pointing at PLC sub-projects. — [ST-LSP TwinCAT integration](https://pirminbleiker.github.io/st-lsp/features/twincat.html); additional extensions `.tcGVL`, `.tcDUT`, `.tcIO`, `.tspProj`, `.splcProj`. — [Copia: Beckhoff](https://docs.copia.io/docs/supported-vendors/beckhoff)
- Beckhoff GitHub org: 58 repositories, including `TF6100_Samples` (TC3 OPC UA; "provided as-is under the Zero-Clause BSD license"; folders `TF6100_OpcUa_Client_Sample`, `TF6100_OpcUa_Server_Sample`, `container-samples`, plus TwinCAT 2 `TS6100_*` PLCopen samples), `TF6310_Samples`, `TF6701_Samples`, `TF6760_Samples`, `TF5500/5550/5560_Samples`, `TF6000_ADS_DOTNET_V4/V5_Samples` (0BSD), `TC170x_Samples`, `Tc3Eventlogger_Samples` (0BSD), `TC1300_Samples`, `TF6300_Samples`, `ADS-over-MQTT_Samples`, etc. Many are labeled "Other" license on GitHub. — [Beckhoff org page 1](https://github.com/orgs/Beckhoff/repositories); [page 2](https://github.com/orgs/Beckhoff/repositories?page=2); [TF6100_Samples](https://github.com/Beckhoff/TF6100_Samples)
- Beckhoff Infosys also distributes samples as `.tpzip` archives and zipped PLC projects (e.g., `TC3_XmlSrv_Samples.zip`). — [EL6685 sample](https://infosys.beckhoff.com/content/1033/el6685/3722233611.html); [TF6421 samples](https://infosys.beckhoff.com/content/1033/tf6421_tc3_xml_server/187140107.html)
- B&R: a 2006 B&R release says its data management "uses XML" and formats "can be documented and generated". — [automation.com](https://www.automation.com/en-us/products/product22/brs-automation-development-software-offers-xml-bas); control.com: the AS project "file structure ... is wide open and able to be manipulated with simple text editors". — [control.com](https://control.com/technical-articles/programming-br-plcs-with-automation-studio/); Copia lists `.apj` (project), `.set` (user settings), `.c`, `.typ`, `.var`. — [Copia: B&R](https://docs.copia.io/docs/git-based-source-control/supported-vendors/bnr)
- PLCnext Engineer: "uncompressed flat format (*.pcwef)" is "designed for source data to be modified directly on the hard disk"; "Compressed Projects (*.pcwex)"; project archive `*.pcweax`. — [PLCnext Engineer Help: File Menu](https://engineer.plcnext.help/latest/File_Menu.htm); the compressed format "enables the default data security provided by PLCnext Engineer". — [Security Guideline](https://engineer.plcnext.help/latest/SecurityGuidelines.htm); MULTIPROG/PLCnext users discuss PLCopen XML "V101"/"V101 ext" export. — [PLCnext forum](https://forum.plcnext-community.net/t/multiprog-export-plcopen-xml-v101-or-v101-ext/10253)
- OpenPLC Editor: GPL-2.0; "contains modified versions of Beremiz and MatIEC", Python 3/wxPython; archived read-only Aug 3, 2026; 580 stars. — [thiagoralves/OpenPLC_Editor](https://github.com/thiagoralves/OpenPLC_Editor); Beremiz: IDE GPLv2+, topic tag `plcopen-tc6`, `plcopen` directory, examples in `tests/projects` and `exemples`. — [beremiz/beremiz](https://github.com/beremiz/beremiz)
- Local evidence: PEAT's fixture `tests/modules/openplc/data_files/Relay_Blink_PLC.zip` contains `plc.xml` with namespace `http://www.plcopen.org/xml/tc6_0201`, `debug-map.json`, and generated `pou_MAIN.cpp` — i.e. PEAT already holds a Beremiz/OpenPLC-style PLCopen TC6 v2.01 project fixture.
- Revolution Pi: PiCtory stores its configuration at `/etc/revpi/config.rsc`; "before the configuration can be used, it must be saved and the driver must be reset". — [RevPi PiCtory docs](https://revolutionpi.com/documentation/pictory/); KUNBUS staff: the file is JSON, piControl "at startup parses this JSON file to load the configuration and variable names", and replacing it is fine "as long as it contains well-formed JSON data"; the GUI copy lives at `/var/www/pictory/projects/_config.rsc`. — [RevPi forum p=7514](https://revolution.kunbus.com/forum/viewtopic.php?p=7514); [RevPi forum p=7519](https://revolutionpi.com/forum/viewtopic.php?p=7519)
- Ignition `.gwbk`: default filename `GatewayName_Ignition-backup-YYYYMMDD-HHMM.gwbk`. — [Ignition 8.3 backup/restore](https://docs.inductiveautomation.com/docs/8.3/platform/gateway/gateway-backup-and-restore); forum: "Rename it as .zip. Then extract the contents." — [IA forum 79511](https://forum.inductiveautomation.com/t/how-open-the-gwbk-file/79511.md); a project export "is a zip of that project folder" whose root folder must equal the project name. — [IA forum 112607](https://forum.inductiveautomation.com/t/clarification-on-extracting-a-single-project-from-ignition-gateway-backup-gwbk/112607); archive contains `db_backup_sqlite.idb` (a CRC failure on it indicated a truncated backup). — [IA forum 58097](https://forum.inductiveautomation.com/t/problem-with-gateway-restore-file-invalid-end-header/58097)
- FUXA: MIT, 5.2k stars; persists "application data (project)" in an `_appdata` directory; SQLite for DAQ history; Docker `frangoteam/fuxa:latest`; port 1881. — [frangoteam/FUXA](https://github.com/frangoteam/FUXA)
- Rapid SCADA: Apache-2.0, 746 stars. — [RapidScada/scada](https://github.com/RapidScada/scada); docs describe an open-source platform supporting OPC UA/Classic, Modbus, MQTT, SNMP. — [Rapid SCADA docs 6.1](https://rapidscada.net/docs/en/6.1/)

### Inferences
- A single PLCopen TC6 XML parser in PEAT (leveraging the embedded PLCopen editor code) would cover CODESYS PLCopen exports, OpenPLC Editor/Beremiz `plc.xml`, and PLCnext/MULTIPROG PLCopen exports; TwinCAT `.TcPOU` is a different (Beckhoff-specific) XML schema but trivially parsed with the standard library, and ST bodies can be extracted directly.
- Beckhoff's 0BSD-licensed sample repos are the best redistributable fixture source found in this research; repos labeled "Other" need a per-repo license check before copying into PEAT's test tree.
- Generating fixtures yourself (e.g., exporting a `.gwbk` from an Ignition trial container, saving a FUXA project, running OpenPLC Editor) avoids redistribution questions entirely; CODESYS `.project`/`.export` fixtures can be generated with the free CODESYS Development System but the IDE is Windows-only.

### Gaps
- No public, redistributable B&R Automation Studio sample project was verified (search found only a Claude plugin that reads `.apj`, and training PDFs).
- Internal structure of CODESYS `.project` (binary vs. container) not documented in any fetched source; a secondary blog claims ABB's `.exp` is "binary-encoded" but this was not verified.
- Whether `.pcwex` is a ZIP of XML was not confirmed; `.pcwef` being text/XML is inferred from "modified directly on the hard disk".
- No verified public `.gwbk` or RevPi `config.rsc` sample files with redistribution terms; TwinCAT 2 `.pro` format not researched.

## Key Question 3: Is the CODESYS V3 protocol documented well enough (public dissector or research) to implement an unauthenticated identity fingerprint?

### Takeaway
Yes, with moderate effort. There is no official specification, but three public artifacts together are sufficient: Microsoft's MIT-licensed CoDe16 repository (a Wireshark dissector for the CODESYS V3 protocol plus an "active tool to extract the CODESYS V3 runtime version of devices"), Kaspersky's 2019 protocol breakdown (four layers, field map, service IDs), and Nozomi's documented passive/active discovery strategy showing that device name, node name, serial number, vendor name and version are obtainable over UDP 1740–1743. Caveat: the CoDe16 repo was archived in June 2026 (still cloneable).

### Cited Findings
- Microsoft CoDe16 repo: MIT license; contains a "Wireshark Dissector for CODESYS V3 proprietary protocol", an "Active tool to extract the CODESYS V3 runtime version of devices", IDA Python scripts, and the white paper; lists CVE-2022-47379 … CVE-2022-47393 (CmpApp, CmpTraceMgr, CmpDevice, CmpAppForce, CmpAppBP, CmpFiletransfer; CVSS 7.5–8.8); "affect all versions of CODESYS V3 prior to version 3.5.19.0"; repo archived read-only June 15, 2026. — [microsoft/CoDe16](https://github.com/microsoft/CoDe16)
- Microsoft blog: protocol "has four layers: block driver, datagram, channel, and services", tag-based encoding; TCP 11740–11743 / UDP 1740–1743; exploitation "requires user authentication"; tested on Schneider Electric Modicon TM251 and WAGO PFC200; tooling "communicates with devices to safely extract the CODESYS version" and `ics-forensics-tools` supports forensic investigation of CODESYS V3 devices. — [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2023/08/10/multiple-high-severity-vulnerabilities-in-codesys-v3-sdk-could-lead-to-rce-or-dos/)
- Kaspersky (Nochvay, 2019): CODESYS "PDU" stack "consisting of four different layers: Block driver layer, Datagram layer, Channel layer and Services layer"; annotated packet with fields "Magic PDU of packet (only for TCP)", receiver/sender lengths, hop info, sender/receiver address, packet type (BLK), channel id, blk id, flags, ack id, checksum, protocol id, service group id, service id, session id, and data tags (CryptType, Challenge, username, encrypted password); example addresses show TCP ports 11740/11743 and sender/receiver IPs embedded in the PDU; service IDs include CmpDevice 0x1, CmpApp 0x2, CmpVisuServer 0x4, CmpLog 0x5, CmpSettings 0x6, SysEthernet 0x7, CmpFileTransfer 0x8, CmpIecVarAccess 0x9, CmpIoMgr 0xb, CmpUserMgr 0xc, CmpTraceMgr 0xf, PlcShell 0x11, CmpAppBP 0x12, CmpAppForce 0x13, CmpAlarmManager 0x18, CmpMonitor 0x1b, CmpCodeMeter 0x1d, CmpCoreDump 0x1f, CmpOpenSSL 0x22; "Enabled encryption between PLC and IDE encrypts only service layer"; name-service components NSServer/NSClient handle discovery; vulnerabilities covered address spoofing, channel hijack, MitM via ADD_SERVICE broadcast, weak password encryption (XOR with fixed key shown), predictable session IDs; conclusion: "All discovered vulnerabilities could have been found by the community if the protocol specification had been available." — [Kaspersky "The fall of CODESYS" (PDF)](https://go.kaspersky.com/rs/802-IJN-240/images/06-Alexander-Nochvay-The-fall-of-CODESYS.-Researching-security-of-the-framework-for-PLC-control.pdf)
- Nozomi Networks' CODESYS discovery strategy: transport UDP only, device-side ports UDP/1740–1743, sensor-side UDP/1740, outbound 72 bytes; collects device type, product name, roles, vendor and node properties `codesys.device_name`, `codesys.node_name`, `codesys.serial_number`, `codesys.vendor_name`, `codesys.version` (items vary by device/configuration). — [Nozomi technical docs](https://technicaldocs.nozominetworks.com/products/discovery/autogenerated/topics/r_discovery_strategies_codesys.html)
- A commercial third-party implementation of "CODESYS V3 TCP" exists (EMQX Neuron south driver), evidence the protocol has been re-implemented outside 3S. — [EMQX Neuron docs](https://docs.emqx.com/en/neuron/latest/configuration/south-devices/codesys3/codesys3.html)
- Claroty Team82 researched the cloud-side CODESYS Automation Server and WAGO PLCs (CVE-2021-29238 CSRF 8.0; CVE-2021-29240 package manager 7.8; CVE-2021-29241 Edge Gateway NULL deref 7.5; CVE-2022-22515 config-file access 7.1). — [Claroty CVE-2021-29238](https://claroty.com/team82/disclosure-dashboard/cve-2021-29238); [control.com summary](https://control.com/news/clarotys-new-research-arm-publishes-report-on-ics-cloud-vulnerabilities/)
- No Forescout CODESYS V3 protocol paper and no CODESYS V3 Nmap NSE script surfaced in searches (Forescout results were absent; NSE search returned only generic Lua dissector projects).

### Inferences
- An unauthenticated PEAT scan fingerprint is realistic: send the UDP name-service discovery request (the 72-byte probe Nozomi describes, reconstructable from the CoDe16 dissector and a capture against the CODESYS Virtual Control container) to UDP 1740 (broadcast or unicast) and parse the response for device name, node name, serial, vendor, version; optionally open TCP 11740 and use the CmpDevice (service group 0x1) version query that CoDe16's active tool performs. Microsoft's statement that exploitation needs authentication implies the version query itself does not, and the datasheet/Nozomi evidence indicates identity is disclosed pre-login.
- Pull of logic/files (CmpFileTransfer 0x8, CmpApp 0x2) requires the authenticated channel with the (historically weak) challenge/response and encrypted service layer; that is a large effort and may raise EULA/reverse-engineering concerns, so "pull" should be scoped to the web/OPC UA/SSH side services or deferred.
- Because Microsoft's tooling exists under MIT, PEAT (GPLv3) can reference it for protocol structure; a Python reimplementation is license-compatible.

### Gaps
- The exact byte layout of the UDP discovery request/response was not extracted (the CoDe16 dissector source was not read; the GitHub page only summarizes folder contents). Expect a day or two of packet-capture work against the Virtual Control container.
- No published count of internet-exposed CODESYS devices was found (search budget exhausted; general ICS exposure figures only: ~70,000 exposed OT devices globally in a 2025 arXiv study — [arXiv 2508.02375](https://arxiv.org/html/2508.02375v1); Censys 54,770 vs Shodan 33,036 Modbus devices — [SANS ISC](https://isc.sans.edu/diary/30860)).

## Key Question 4: Does WAGO's open firmware SDK or firmware images enable a QEMU-based test target?

### Takeaway
Not as published. WAGO's SDKs (MPL-2.0) build real SD-card images (`sd.hdimg`) for ARM PFC100/PFC200 G1/G2, CC100, PFC300 and TP600 via PTXdist, with no QEMU/emulation target mentioned anywhere; a "Docker base image of WAGO's PFC firmware" exists but is a minimal userland for the PFC hardware platform, not a WBM/CODESYS emulator. Official firmware release repositories exist, but reproducing the WBM web stack under QEMU would be a bespoke engineering project.

### Cited Findings
- `pfc-firmware-sdk`: MPL-2.0; "Firmware SDK for PFC200-G1 and PFC100 family"; Ubuntu 16.04.5 host, git-lfs, precompiled `gcc-Toolchain-2019.12`, PTXdist 2017.11.1; `ptxdist go` takes "30 minutes up to a few hours"; `ptxdist images` yields `sd.hdimg` (~204 MB) to `dd` onto an SD card; default users root/admin/user; covers 750-8100/8101/8102 (PFC100) and 750-8202/8203/8204/8206/8207/8208 variants (PFC200); 42 commits; no QEMU mentioned. — [wago/pfc-firmware-sdk](https://github.com/wago/pfc-firmware-sdk)

- `pfc-firmware`: "official Wago firmware releases for 750-8xxx(PFC) series"; notes that WBM requires clearing the browser cache after update; recommends original WAGO SD cards. — [WAGO/pfc-firmware](https://github.com/WAGO/pfc-firmware)

### Inferences
- A QEMU target would require booting the PTXdist-built ARM image under `qemu-system-arm` with a board model matching the PFC's SoC and stubbing the KBus/IO drivers; nothing in WAGO's repos supports this, and the WBM/WDA PHP/web stack would also need to come up without hardware daemons. Effort: large, with uncertain payoff.
- Since PFC firmware >= 23 embeds CODESYS V3, a generic CODESYS scan module (KQ3) covers WAGO identity over UDP 1740/TCP 11740 without WAGO-specific code; WAGO-specific WBM fingerprinting (HTTPS banners/paths) would need hardware or captured responses.

### Gaps
- No official documentation of a WAGO "WDA" REST API was found; the only WBM evidence is manuals describing WBM as a "configuration aid" and security advisories about WBM plugins (see per-candidate section). Treat a WDA/REST-based pull as unverified.
- License text of `pfc-firmware` and `pfc-firmware-base-image` not visible in fetched content.

#### 10. OPC UA as cross-vendor identity source
- FindServers "does not require message security"; `authenticationToken` "should be null" and is ignored; returns `ApplicationDescription` records with `applicationUri`, `applicationName`, `discoveryUrls`. — [OPC UA Part 4 §5.5.2](https://reference.opcfoundation.org/Core/Part4/v105/docs/5.5.2); `BuildInfo` structure: `productUri`, `manufacturerName`, `productName`, `softwareVersion`, `buildNumber`, `buildDate`. — [OPC UA Part 5 §12.4](https://reference.opcfoundation.org/Core/Part5/v105/docs/12.4)
- asyncua: LGPL-3.0, Python >= 3.10, client+server, `uadiscover` (find_servers/get_endpoints/find_servers_on_network). — [FreeOpcUa/opcua-asyncio](https://github.com/FreeOpcUa/opcua-asyncio)
- OPC UA is embedded across candidates: CODESYS runtime links the OPC Foundation stack (Kaspersky slide "What is inside CODESYS Runtime?: OPC Foundation, OpenSSL, SQLITE"). — [Kaspersky PDF](https://go.kaspersky.com/rs/802-IJN-240/images/06-Alexander-Nochvay-The-fall-of-CODESYS.-Researching-security-of-the-framework-for-PLC-control.pdf); Ignition Maker includes the OPC UA module. — [Maker docs](https://docs.inductiveautomation.com/docs/8.1/other-editions/ignition-maker-edition); TwinCAT TF6100 OPC UA server sample containers exist. — [TF6100_Samples](https://github.com/Beckhoff/TF6100_Samples); FUXA and Rapid SCADA support OPC UA (above).
- (i) PARSE: n/a (identity only; optional nodeset XML export parse). SCAN without hardware: YES (asyncua server in CI; 4840/TCP). Effort: small.

- Shortlist ranked for PARSE+SCAN without hardware: (1) OpenPLC v3 — both YES, days; (2) OPC UA generic — SCAN YES, days, adds identity to many other modules; (3) CODESYS V3 generic — both YES (with store-account/EULA caveat for CI image), weeks, highest device coverage and strongest advisory record; (4) Ignition — both YES with self-generated fixtures, weeks; (5) FUXA/Rapid SCADA — both YES, days, low criticality; (6) Beckhoff TwinCAT 3 — PARSE YES (best fixtures), SCAN writable from spec but not CI-testable; (7) PLCnext — PARSE likely, SCAN blocked by CodeMeter; (8) Revolution Pi — PARSE only; (9) WAGO-specific — neither established hardware-free (CODESYS module covers identity); (10) B&R — PARSE plausible, SCAN not CI-testable.
