# OT Network Infrastructure Devices as PEAT Module Candidates (firewalls, industrial switches, routers, cellular gateways, serial device servers)

Research date: 2026-10-31. Scope: network-infrastructure devices only; Fortinet FortiGate is used only as the baseline. Method: web search + primary-source fetches (vendor docs, GitHub, PyPI JSON API, CISA). The shared WebSearch budget ran out partway through, so several second-tier vendors (Siemens SCALANCE, Phoenix Contact, Red Lion, Advantech, Antaira, InHand, Digi IX/WR, Hirschmann config schema) are documented only to the extent the first search round covered them; those are flagged in Gaps.

Coordinator clarification applied: the baseline target for a new module is PARSE + SCAN. Ranking in the Inferences sections weights (1) redistributable sample vendor files for parser fixtures and (2) a free, network-reachable soft target that answers on real TCP/UDP ports for CI scan tests. Pull/push are secondary. A parse/scan achievability matrix is in the final section.

PEAT baseline facts used for "fit" judgments (from the repository at /home/user/PEAT): protocol code exists for SNMP (`pysnmp-lextudio==5.0.34`), FTP, Telnet (forked telnetlib), SSH (`paramiko==2.12.0` + `scp`), HTTP (`requests==2.29.0`), serial (`pyserial==3.4`), plus `scapy==2.6.1` for ARP/ICMP/TCP-SYN host discovery (`peat/protocols/discovery.py`). There is no shared Modbus or NETCONF protocol module (ad-hoc Modbus exists only inside the Woodward and Camlin modules). XML parsing is already used by several modules (Rockwell L5X, SEL RTAC, Schneider M340/SAGE). The Fortinet module (`peat/modules/fortinet/`, ~1,660 lines across 5 files) parses `.conf`, debug logs and FortiAnalyzer/memory event logs, and pulls over SSH/SCP and HTTPS; this is the effort yardstick ("medium") for a text-config firewall module.

## Key Question 1: Which network OSes can legally be run for free in CI (Docker/QEMU) for scan/pull testing?

### Takeaway
OPNsense, VyOS rolling, MikroTik CHR (free tier) and Juniper vJunos are the only candidates that are simultaneously free, time-unlimited, downloadable without a sales process, and permitted for lab use; all four are KVM/QEMU VMs (not native containers) and so need a KVM-capable Linux runner (GitHub's hosted 2-vCPU Linux runners have exposed KVM since April 2024). Cisco images are legally confined to CML (free tier = 5 nodes, VMware/bare-metal only), pfSense CE's ISO now sits behind Netgate's store/installer flow, and Palo Alto VM-Series is a 30-day trial with reported manual approval, making those three poor CI targets.

### Cited Findings

**CI runner virtualization**
- GitHub announced (2024-04-02) that 2-vCPU GitHub-hosted Linux runners can use hardware-accelerated (KVM) virtualization; previously 4+ vCPU runners were required. The example workflow adds a udev rule (`/etc/udev/rules.d/99-kvm4all.rules`, group `kvm`, mode 0666) before launching an emulator. Windows and macOS runners are not mentioned. — [GitHub Changelog](https://github.blog/changelog/2024-04-02-github-actions-hardware-accelerated-android-virtualization-now-available/)
- Earlier (2022) GitHub runner-images issues state nested virtualization was unavailable on hosted Linux runners and only macOS runners supported it then; a Feb 2023 changelog added it to larger Linux/Windows runners. — [actions/runner-images discussion #7191](https://github.com/actions/runner-images/discussions/7191); [actions/runner-images issue #183](https://github.com/actions/runner-images/issues/183)
- containerlab (Docker-based lab orchestrator) lists VM-in-container kinds for Juniper vJunos-router/vJunos-switch/vSRX/vMX, MikroTik RouterOS (`mikrotik_ros`) and CHR (`mikrotik_chr`), VyOS, Palo Alto PAN-OS (`paloalto_panos`), Fortinet FortiGate, Cisco CSR1000v/Cat8000v/Cat9000v/N9kv/FTDv/XRv, FreeBSD, OpenBSD, OpenWRT and a "Generic VM"; native-container kinds include Cisco IOL (`cisco_iol`), Juniper cRPD/cSRX, Arista cEOS, Nokia SR Linux, FRR, SONiC. pfSense/OPNsense and Cisco IOSv/ASAv are not listed. — [containerlab kinds](https://containerlab.dev/manual/kinds/)
- The `hellt/vrnetlab` fork used by containerlab says it actively supports Arista vEOS, Cisco XRd/XRv9k/XRv/FTDv, Juniper vMX/vSRX/vJunos-switch/vJunos-router/vJunosEvolved, Nokia SR OS, OpenBSD, FreeBSD and Ubuntu; other vendor directories are "left untouched and can be contributed back by the community." Users build the images themselves. — [hellt/vrnetlab](https://github.com/hellt/vrnetlab)

**OPNsense (Deciso)**
- License: BSD 2-Clause; copyright holders include Deciso B.V., Ad Schellevis and Franco Fichtner (2014-2026). — [opnsense/core LICENSE](https://raw.githubusercontent.com/opnsense/core/master/LICENSE)
- Official images: `dvd` (ISO), `vga` (USB), `serial` (USB, 115200 serial console) and `nano` (embedded, pre-installed); x86-64 only; downloaded from community mirrors listed on opnsense.org. Default credentials: live/GUI `root`/`opnsense`, SSH `root` or `installer` with password `opnsense`. The installer is interactive (keymap, UFS/ZFS, disk, swap, root password prompts); no unattended mode is documented on that page. No official VM/cloud image is confirmed on the install page (it points to a separate "Virtual & Cloud-Based Installation" chapter). — [OPNsense install docs](https://docs.opnsense.org/manual/install.html)
- Built-in REST API: `https://<host>/api/<module>/<controller>/<command>/[params]`, GET to read, POST to create/update/act, JSON bodies, authentication with an API key + secret used as HTTP basic username/password; endpoint reference is auto-generated and split into Core, Plugins and Business-edition APIs; the docs recommend watching browser `/api/` traffic to learn parameters. — [OPNsense API docs](https://docs.opnsense.org/development/api.html)
- The `nano` image can be converted for automated VM setup with `qemu-img convert -f raw -O qcow2`; maintainers pointed to the tools repo README for "vm" image builds. — [opnsense/tools issue #385](https://github.com/opnsense/tools/issues/385)
- Community Docker image `koichirok/docker-opnsense` runs OPNsense as a KVM VM inside a container; requires `--cap-add NET_ADMIN` and `/dev/kvm`; tags `24.1` and `25.1.3-image`; author states it is "intended for testing purposes and not designed for use in a production environment"; last updated over one year ago (image ~836 MB). — [Docker Hub](https://hub.docker.com/r/koichirok/docker-opnsense)
- A NationTech "Harmony" example boots an OPNsense VM via libvirt, creates an API key over SSH with a PHP script, installs a plugin via the firmware API and asserts configuration via REST — an existing pattern for unattended OPNsense API testing. — [Harmony opnsense_vm_integration README](https://git.nationtech.io/NationTech/harmony/src/branch/master/examples/opnsense_vm_integration/README.md)

**pfSense CE (Netgate)**
- Netgate's download page says CE and Plus are installed via the "Netgate Installer" and the Download link "redirects to our online store"; a 2.8.1 DVD (ISO) installer and memstick images are listed. — [pfsense.org/download](https://www.pfsense.org/download/)
- Netgate forum users report the store/installer flow is confusing (installer "seems to only be able to install pfSense in a VM, or in a bare-metal machine"; "There is no ISO"; no CE 2.8.1 ISO at one point). — [Netgate forum post 1229462](https://forum.netgate.com/post/1229462); [post 1219562](https://forum.netgate.com/post/1219562)
- A Lawrence Systems forum thread marked "solved" points to Netgate's FTP mirror `sgpfiles.netgate.com` for account-free ISO downloads (not verifiable from this session: the host is outside the allowed network domains). — [Lawrence Systems forum](https://forums.lawrencesystems.com/t/solved-download-pfsense-iso-without-account/22836)
- The configuration is a single XML file at `/conf/config.xml` holding "all configuration settings including settings for packages"; it is downloadable from Diagnostics > Backup/Restore; the docs do not publish an element-by-element schema. — [Netgate docs: XML Configuration File](https://docs.netgate.com/pfsense/en/latest/config/xml-configuration-file.html); [Backup and Recovery](https://docs.netgate.com/pfsense/en/latest/backup/)
- pfSense has no built-in REST API; the community `pfSense-pkg-RESTAPI` (REST + GraphQL, Apache 2.0, maintained by Jared Hendrickson, "not affiliated with Netgate") works on CE and Plus and ships Swagger docs under System > REST API. — [pfrest.org](https://pfrest.org/)

**VyOS**
- Three channels: nightly builds (free; "it really is a GitHub release"), monthly snapshots, and LTS. LTS prebuilt images are for subscribers/contributors ("pay for binaries"), while anyone can build LTS from source; "VyOS Stream" (quarterly preview of the next LTS) is a free download. — [vyos.net/get](https://vyos.net/get); [vyos.io community subscriptions](https://vyos.io/subscriptions/community); [VyOS support FAQ "Is it free to use VyOS?"](https://support.vyos.io/support/solutions/articles/103000096259-is-it-free-to-use-vyos-)
- HTTP API: every endpoint except `/info` needs an API key sent as the `key` form field; `/retrieve` (`showConfig`, `returnValues`, `exists`) returns the whole structured config with an empty path; `/show` with `["configuration","commands"]` returns the running config as flat `set` commands; `/configure`, `/config-file` (save/load/merge, default `/config/config.boot`), `/image`, `/generate`, `/reboot` etc. — [VyOS HTTP API docs](https://docs.vyos.io/en/latest/automation/vyos-api.html)

**MikroTik RouterOS CHR**
- CHR images are provided as RAW (.img), VMware (.vmdk), Hyper-V (.vhdx) and VirtualBox (.vdi); QEMU/KVM is a supported hypervisor (bhyve is not); minimum 256 MB RAM / 128 MB disk. The **Free** license runs indefinitely with a 1 Mbps upload cap per interface and all other features unrestricted; a 60-day P1/P10/P-Unlimited trial requires a MikroTik.com account (`/system license renew`); cloned images need `/system license generate-new-id`. Downloads: mikrotik.com/download, CHR section. — [MikroTik CHR docs](https://help.mikrotik.com/docs/spaces/ROS/pages/18350234/Cloud+Hosted+Router+CHR); [CHR licensing](https://manual.mikrotik.com/docs/getting-started/routeros-licensing/chr/chr-licensing)
- REST API (RouterOS >= 7.1beta4): HTTPS on the `www-ssl` service at `https://<router>/rest/<menu path>`, HTTP basic auth with console credentials (default `admin`, empty password), GET=print, PUT=add, PATCH=set, DELETE=remove, POST runs any console command including `/rest/export` with `compact`/`file` parameters. — [RouterOS REST API docs](https://help.mikrotik.com/docs/spaces/ROS/pages/47579162/REST+API)
- A (Russian-language) Habr write-up documents testing RouterOS through its API inside Docker with headless QEMU. — [Habr post 498012](https://habr.com/en/post/498012)

**Juniper vJunos-switch / vJunos-router**
- Juniper offers vJunos-router and vJunos-switch "free for non-production test environments" with "no time limit"; download requires accepting the EULA at the support download page. (Search-indexed page; the page itself returned HTTP 404 in this session, so wording is from search-result snippets.) — [Juniper vJunos labs page](https://www.juniper.net/us/en/dm/vjunos-labs.html)

**Cisco IOS / IOS-XE / ASA**

### Inferences
- For PEAT's GitHub Actions matrix, only the **Linux** job can realistically boot a network OS VM (KVM exposed on hosted Linux runners since 2024); Windows/macOS jobs would need to mock or skip scan/pull tests. Any VM-backed test should be an opt-in integration job, not a unit test.
- **OPNsense** is the best free firewall soft target: BSD-licensed, anonymous mirror downloads, documented key/secret REST API, known default credentials, and two existing community automation patterns (KVM-in-Docker image; libvirt+API-key bootstrap). The missing piece is an unattended install; the `nano` raw image (pre-installed) converted to qcow2 avoids the interactive installer entirely.
- **pfSense CE** is technically equivalent (same config.xml lineage, SSH, 2.8.x) but its distribution now flows through Netgate's store/installer; account-free mirrors exist per community reports but could not be verified here. Treat pfSense as a parse-first target and reuse the OPNsense VM for scan tests where behaviour overlaps (HTTPS login page, SSH banner, SNMP), while clearly separating the two in fingerprints.
- **VyOS rolling** and **MikroTik CHR** are the lowest-friction router soft targets: both are free, time-unlimited, boot in QEMU within a minute or two, and expose SSH + an HTTP(S) API out of the box. CHR's 1 Mbps/interface cap is irrelevant for scan/pull tests.
- **vJunos** is legally clean and free but heavy (4 vCPU / 5 GB, ~15 min boot, cannot run nested in a VM, so it will not run inside a hosted-runner VM that lacks nested virt... hosted Linux runners do expose KVM, but the 15-minute boot makes it a nightly-job candidate at best).
- **Cisco** cannot be exercised in CI without violating the CML image license or paying; the free CML tier is a developer-desktop tool (VMware OVA, Cisco account), and DevNet always-on sandboxes are shared, flaky public resources unsuitable as deterministic CI fixtures. Cisco is therefore parse-only in practice, with scan fingerprints developed from documentation/recorded SNMP walks rather than a live soft target.
- **Palo Alto** is a 30-day, manually approved trial: fine for one-off developer validation, not for recurring CI.

## Key Question 2: For parse-only candidates, are there large public corpora of sample configs (ntc-templates, Batfish, GitHub)?

### Takeaway
Yes for the mainstream NOSes: ntc-templates (Apache 2.0) ships ~1,100 TextFSM templates with per-command `.raw` fixtures across ~80 platforms (Cisco IOS/ASA/NX-OS/XR, Junos, PAN-OS, RouterOS, VyOS, EdgeRouter, FortiOS, etc.), Batfish (Apache 2.0) ships grammar test configs for Cisco/ASA/XR/Junos/PAN-OS/FortiOS, and VyOS's own repo has 52 smoketest `config.boot` files. For OT-specific switches and gateways (Moxa, RUGGEDCOM, Hirschmann, Westermo, Sierra Wireless, Cradlepoint, Digi) no public fixture corpus was found; sample files would have to be synthesized from vendor manuals or contributed by users.

**Per-platform sample files**
- VyOS: `vyos-1x/smoketest/configs` holds 52 sample configuration files (e.g. `basic-vyos`, `bgp-rpki`, `ospf-small`, `vpn-openvpn`, `firewall-groups-name`, `nat-basic`, `qos-basic`, `vrf-ospf`) plus `assert` and `no-load` subdirectories. — [vyos-1x smoketest configs](https://github.com/vyos/vyos-1x/tree/current/smoketest/configs)
- OPNsense: `src/etc/config.xml.sample` in opnsense/core is a minimal `<opnsense>` document with `<system>` (hostname, domain, timezone, bcrypt root hash, `admins` group gid 1999), `<interfaces>` (wan DHCP, lan 192.168.1.1/24 with placeholder device names `mismatch0/1`), `<dnsmasq>`, `<unbound>`, `<nat>`, empty `<filter>`, `<rrd>`, `<ntpd>` and an `<OPNsense>` model section with two LAN-to-any rules; it has no `<version>`, `<dhcpd>`, `<snmpd>` or `<syslog>` elements, so it is only a partial fixture. — [opnsense/core config.xml.sample](https://raw.githubusercontent.com/opnsense/core/master/src/etc/config.xml.sample)
- pfSense: Netgate's docs describe `config.xml` but publish no schema; the pfSense source repository's default `config.xml` could not be retrieved in this session (HTTP 404 on raw/tree URLs and GitHub API access is restricted for this session). — [Netgate XML Configuration File](https://docs.netgate.com/pfsense/en/latest/config/xml-configuration-file.html)
- MikroTik: `/export` produces a plain-text `.rsc` of console `add`/`set` commands; `compact` is the default since v6rc1, `terse` puts each setting on one full-path line, `verbose` includes defaults, `show-sensitive` reveals secrets, `file=` writes `<name>.rsc`, `path=` filters menus (7.13+ exports sub-menus). Exports omit user passwords, certificates, SSH keys, Dude and User Manager data. `/system backup` is a binary, optionally encrypted, full clone. — [RouterOS Configuration Management](https://manual.mikrotik.com/docs/getting-started/configuration-management/)
- Cradlepoint NCOS: the router's config store has `config/` (persisted, GET/PUT/POST/DELETE, schema defined by a DTD), `status/` (read-only runtime), `control/` (one-shot actions) and `state/` trees; REST endpoints `/api/config/{path}`, `/api/status/...`, `/api/dtd/config/{path}` are reachable with HTTP basic auth (`-u admin:pass`), responses wrapped in `success`/`data`, writes are form-encoded `data=`. ## Key Question 3: For Moxa / Hirschmann / RUGGEDCOM, how well documented are their config export formats and discovery protocols?

### Takeaway
RUGGEDCOM ROS is the best documented of the three: Siemens' user guide states the configuration is a single comma-delimited ASCII `config.csv` that can be diffed/edited/partially uploaded over TFTP/SFTP/XMODEM, lists every management port, the RUGGEDCOM MIBs and a Modbus/TCP register map (Product Identification at register 0x0000), but its L2 discovery protocol (RCDP) is described functionally only. Moxa's UDP/4800 discovery protocol is publicly reverse-engineered (8-byte request `01 00 00 08 00 00 00 00`, 24-byte reply starting `0x81` with model code, MAC and IP) via Metasploit and a 2019 Habr write-up, while its `.ini` config schema is undocumented. Hirschmann's HiDiscovery v1 is an unroutable Layer-2 protocol with no public frame specification; v2 runs over SNMP; its XML config format is editable text but schema-less.

### Cited Findings

**Siemens RUGGEDCOM ROS (RS416 user guide, ROS v4.1, 12/2014, RC1170-EN-01)** — all from [Siemens ROS v4.1 RS416 User Guide (PDF)](https://cache.industry.siemens.com/dl/files/570/108275570/att_59166/v1/ROS_RS416_User-Guide_EN.pdf)
- Files on the device ("Key Files"): `main.bin` (ROS firmware), `boot.bin` (boot loader), `fpga.xsvf`, `config.csv` ("the complete configuration database, in the form of a comma-delimited ASCII text file"), `banner.txt`; flash listing also shows `syslog.txt`, `crashlog.txt`, `ssh.keys`, `config.bak`, `factory.txt`.
- "The device configuration file for ROS is a single CSV (Comma-Separate Value) formatted ASCII text file, named config.csv. It can be downloaded from the device to view, compare against other configuration files, or store for backup purposes. It can also be overwritten by a complete or partial configuration file uploaded to the device." The file may be encrypted with a passphrase ("Do not edit an encrypted configuration file. Any line that has been modified manually will be ignored."). ROS "also has the ability to accept partial configuration updates" (example: a file containing only Ethernet port 1 parameters). Editing with text editors, diff/patch and source-control systems is explicitly endorsed.
- Transfer methods: XMODEM over console, TFTP client (`tftp <addr> get|put <src> <dst>`), TFTP server (`tftp -i <ip> put ... main.bin`), SFTP server over SSH.
- Default service/port table: Telnet TCP/23, HTTP TCP/80 (redirects to 443), HTTPS TCP/443, RSH TCP/512, TFTP UDP/69, SFTP TCP/22, SNMP UDP/161, SNTP UDP/123, SSH TCP/22, plus RCDP (L2); several are "only available through two management interfaces."
- RUGGEDCOM Discovery Protocol (RCDP): Layer 2 only, used by the Windows "RUGGEDCOM Explorer" tool to discover unconfigured devices; it retrieves "basic network configuration, ROS version, order code, and serial number", controls LEDs, sets basic parameters; "ROS responds to RCDP requests only"; Explorer tries to disable RCDP on exit and ROS auto-disables RCDP "after approximately one hour of inactivity"; RCDP "is not compatible with VLAN-based network configurations." The frame format is not specified in the guide.
- ModBus management: read-only status via Modbus function codes 0x03/0x04 (plus some writable operator registers); the memory map starts with register 0x0000, 16 registers, "Product Identification", text, read-only.
- SNMP: supported MIBs include `RUGGEDCOM-MIB` (enterprise SMI), `RUGGEDCOM-TRAPS-MIB`, `RUGGEDCOM-SYS-INFO-MIB`, `RUGGEDCOM-SERIAL-MIB`, `RUGGEDCOM-POE-MIB`, `RUGGEDCOM-STP-MIB` plus RC-prefixed agent-capability files for IF-MIB, BRIDGE-MIB, Q-BRIDGE-MIB, LLDP-MIB, RMON-MIB, IP/TCP/UDP MIBs. A DHCP vendor-specific "Vendor-ID: 15004" appears in the guide.
- Device identification fields exposed in the UI: MAC address, Order Code (up to 57 chars), Classification, Serial Number (31 chars), Boot Version, Main Version; `flashfiles info main.bin` prints "Firmware version : v4.1.0".
- Siemens also publishes a separate "RUGGEDCOM EXPLORER" user guide (RCDP tool, has an `RCEXPLORER.ini` appendix) and ROS v4.3 guides with "Uploading/Downloading Files Using XMODEM / TFTP / SFTP" sections. — [RUGGEDCOM EXPLORER User Guide (third-party mirror)](https://www.siemens-pro.ru/docs/ruggedcom/EXPLORER_User-Guide_EN.pdf); [ROS v4.3 RS900M guide (Siemens)](https://cache.industry.siemens.com/dl/files/215/109737215/att_953075/v1/ROS_v4.3_RS900M_User-Guide_FR.pdf)

**Moxa (NPort / OnCell / MGate discovery; EDS/MDS switches)**
- Metasploit `auxiliary/scanner/scada/moxa_discover`: sends 8 bytes `\x01\x00\x00\x08\x00\x00\x00\x00` to UDP/4800 (broadcast 255.255.255.255 or unicast); byte 0 = function 0x01 (discovery/identify), byte 3 = payload length; a valid reply is exactly 24 bytes, starts with function|0x80 = `0x81`, and carries the Moxa OUI `00:90:e8` at bytes 14-16. Tested on NPort 6250 firmware 1.13/1.15; author Patrick DeSantis (Cisco Talos), derived from K. Reid Wightman; references CVE-2016-9361, Digital Bond "Serial Killers" (2016-10-25) and Moxa FAQ id 646. — [moxa_discover.rb source](https://raw.githubusercontent.com/rapid7/metasploit-framework/master/modules/auxiliary/scanner/scada/moxa_discover.rb); [Rapid7 module page](https://www.rapid7.com/db/modules/auxiliary/scanner/scada/moxa_discover/)
- Habr (2019-12-03, work from 2017) documents the same exchange from a Wireshark capture of the NPort Administration Suite: request = 2-byte function `01 00`, 2-byte big-endian length 8, 4 undefined bytes; reply = function `81 00`, length 24, a 6-byte model identifier (e.g. `12 03 00 80 32 03` -> NPort 5232, looked up in `dsci.dll`), MAC `00 90 e8 ...`, IP (e.g. `c0 a8 7f fe`). Also documents NPort TCP 966-969 (control: open/close COM, baud, buffer status; replies like `10 4f 4b` "OK"), TCP 950-953 (serial data), TCP 4900 (device configuration) and TCP 80 (web). The author built an NPort emulator but published only a protocol PDF on a personal blog, not code. — [Habr post 478642](https://habr.com/ru/post/478642)
- The companion Metasploit "Moxa Credential Recovery" module exploits CVE-2016-9361 (unauthenticated credential retrieval over the same UDP/4800 service). — [Packet Storm: moxa_discover](https://packetstormsecurity.com/files/180949/moxa_discover.rb.txt); [Metasploit commit adding Moxa credential recovery](https://cdn05042023.gitlink.org.cn/dnrops/metasploit-framework/commit/11da7c7c815ea2206b261764d7acc4ad5ef649be)
- Fortinet publishes an application-control signature for "Moxa UDP Device Discovery", evidence the protocol is recognized by mainstream DPI vendors. — [FortiGuard app control 46478](https://www.fortiguard.com/appcontrol/46478)
- Moxa EDS switch configuration: web-GUI TFTP backup yields an `.ini`-style text file; CLI `copy running-config tftp` yields a CLI-style file (community report). EDS manuals describe exporting the "entire configuration" to a text file editable in Notepad. No official `.ini` schema found. — [Unimus forum](https://forum.unimus.net/viewtopic.php?p=3946); [Moxa EDS-518A manual](https://www.manualsonline.com/manuals/mfg/moxa_technologies/eds518a_series.html?p=85)
- CISA advisories: ICSA-22-207-04 (NPort 5110 fw 2.10, CVE-2022-2043/2044, CVSS 8.2/7.5, sectors Critical Manufacturing/Energy/Transportation, worldwide, 2022-07-28); ICSA-20-056-04 (EDS-G516E and EDS-510E fw <= 5.2, 7 CVEs, four at CVSS 9.8, sectors Critical Manufacturing/Energy/Water & Wastewater, 2020-03-26); ICSA-17-320-01 (NPort 5110/5130/5150); ICSA-20-287-01 (NPort IAW5000A-I/O); ICSA-21-187-01; WaterISAC-relayed July 2024 advisory on EDS-G508E/G512E/G516E uncontrolled resource consumption; CERT-FR 2025-AVI-0104 (Feb 2025) on Moxa EDS CVE-2024-9404 / CVE-2024-7695. — [ICSA-22-207-04](https://www.cisa.gov/news-events/ics-advisories/icsa-22-207-04); [ICSA-20-056-04](https://www.cisa.gov/news-events/ics-advisories/icsa-20-056-04); [ICSA-17-320-01](https://vulners.com/ics/ICSA-17-320-01); [ICSA-20-287-01](https://qkl.seebug.org/vuldb/ssvid-98408); [ICSA-21-187-01](https://www.cisa.gov/uscert/ics/advisories/icsa-21-187-01); [WaterISAC July 2024](https://waterisac.org/node/12586); [CERT-FR 2025-AVI-0104](https://db.gcve.eu/vuln/certfr-2025-avi-0104)

**Hirschmann (Belden) Classic / HiOS / HiSecOS**
- Belden's KB: both the standalone HiDiscovery tool and HiView use "the so called HiDiscovery protocol" but different versions. v1 is a pure Layer-2 protocol, not routable, used by all standalone HiDiscovery applications and "still supported in the latest software releases of ClassicSwitch, HiOS and HiSecOS"; v2 "works over SNMP and can therefore also be routed" and is used in HiView from v03.0.00. No frame/port specification is given. (KB pages redirect to a login portal when fetched directly; wording from indexed snippets.) — [Belden KB: HiView vs standalone discovery scans](https://hirschmann-support.belden.com/kb/articles/what-are-the-differences-between-the-scans-on-the-discovery-tab-in-hiview-and-the-independent-); [Belden KB (second article)](https://hirschmann-support.belden.com/kb/articles/what-are-the-differences-between-the-scans-in-the-discovery-tab-in-hiview-and-the-standalone-a)

**Comparator: Lantronix serial servers (UDS/XPort/xPico) discovery**
- Lantronix docs: applications such as DeviceInstaller issue discovery queries "according to the Lantronix Discovery Protocol operating on UDP port 30718 (0x77FE)"; discovery is enabled by default and can be disabled per interface via the "Discovery Query Port" setting (Web Manager / CLI / XML `configgroup Discovery`). — [Lantronix xPico 600 UG: Network Discovery](https://docs.lantronix.com/products/xpico-600/1.0/ug/networking-services/network-discovery/)
- UDS-10 manual: a UDP listener on port 30718 (0x77FE); replies go to the source port; "the first three bytes of the UDP data block should be set to zero", the fourth byte selects the command. — [Lantronix UDS-10 user guide p.87](https://powertool.manualsonline.com/manuals/mfg/lantronix/uds10_900207.html?p=87)
- Metasploit `lantronix_telnet_password` sends `00 00 00 F8` to UDP/30718 (optionally TCP), accepts a reply whose byte 3 is `0xF9` as the "setup record", and reads the Telnet password from bytes 12-15 (`00 00 00 00` = no password); tested on Device Server V5.8.0.1. — [lantronix_telnet_password.rb](https://raw.githubusercontent.com/rapid7/metasploit-framework/master/modules/auxiliary/scanner/telnet/lantronix_telnet_password.rb); [Rapid7 module page](https://www.rapid7.com/db/modules/auxiliary/scanner/telnet/lantronix_telnet_password)

- Acunetix rates the Lantronix 30718 password disclosure CVSS 10.0; Tofino published firewall-rule guidance for the protocol; Daktronics tells customers to disable 30718 after audits. — [Acunetix](https://acunetix.com/vulnerabilities/network/vulnerability/lantronix-device-server-password-disclosure); [Tofino](https://www.tofinosecurity.com/node/291); [Daktronics KB](https://www.daktronics.com/en-us/support/kb/000020121)

### Inferences
- **RUGGEDCOM ROS parse** is achievable without hardware at the "small" end of medium: the config is CSV/ASCII with documented partial-file examples in the guide, so a parser plus synthetic fixtures can be built from the manual; the risk is that only fragments (not a full `config.csv`) appear in public documents, so first-run fidelity against a real file is uncertain. **RUGGEDCOM scan** over IP is feasible from documentation alone using PEAT's existing stack (SNMP `RUGGEDCOM-MIB`/`RUGGEDCOM-SYS-INFO-MIB` OIDs, HTTPS/HTTP banner on 80/443, SSH/SFTP on 22) and could add a Modbus/TCP read of register 0x0000 (Product Identification), but there is no emulator; RCDP (L2) is undocumented publicly and auto-disables after an hour, so it is not a practical scan vector.
- **Moxa scan** is the strongest "documented wire protocol, no emulator" case: the UDP/4800 request/reply is fully known (request bytes, reply length, OUI offset, model-code bytes, MAC, IP), fits PEAT's scapy/socket capabilities, and a 30-line Python mock responder can serve as the CI fixture. Serial-server fingerprints can additionally use TCP 950/966/4900 banners. **Moxa parse** is blocked on the undocumented `.ini`/CLI export schemas unless a user contributes samples (NPort web/Telnet export format was not found at all).
- **Hirschmann** is the weakest of the three for hardware-free work: HiDiscovery v1 frames are not publicly specified, v2 is just SNMP (so a generic SNMP sysObjectID fingerprint is the realistic scan path), and the XML export lacks a public schema. Parse would rely on `show running-config script all` text (IOS-like CLI, no public fixtures found) or user-supplied XML.
- **Lantronix** discovery is as well documented as Moxa's (4-byte probe `00 00 00 F8`, reply type `0xF9`, password offset known from the Metasploit source) and would be a cheap sibling scan module; the setup record's remaining field offsets (IP/netmask/gateway) were not found in the sources fetched.
- Security context cuts both ways: the discovery services PEAT would probe (Moxa 4800, Lantronix 30718) are the same ones that leak credentials (CVE-2016-9361; Acunetix CVSS 10), so PEAT's scan must stay read-only and document that probing may trigger IDS signatures (FortiGuard has one).

### Gaps
- RCDP (RUGGEDCOM) and HiDiscovery v1 (Hirschmann) frame formats: no public specification or open-source implementation was found; both are Layer-2 and tool-specific (RUGGEDCOM Explorer, HiDiscovery). Wireshark dissector availability was not checked (search budget exhausted).
- Moxa NPort configuration export format (web console "Export" / Telnet) and the `.ini` schema for EDS/MDS switches: not found.
- Moxa firmware download terms (public vs login) were not verified.
- RUGGEDCOM ROX II (Linux/ConfD-based RX1500/RX5000 line) configuration format and Siemens SCALANCE configuration formats were not researched (search budget exhausted after first attempt returned nothing useful).
- Siemens ProductCERT / CISA advisory counts for RUGGEDCOM and Hirschmann were not compiled.
- The RUGGEDCOM guide's "Vendor-ID: 15004" appears in a DHCP vendor-specific context; whether 15004 is also the SNMP enterprise arc used in `sysObjectID` was not verified.

### Inferences
- **Parse + scan both achievable without hardware (recommend first):** OPNsense (and pfSense sharing the parser), MikroTik RouterOS/CHR, VyOS, Junos/vJunos. All four have free, time-unlimited, lab-licensed VMs that answer on real TCP ports plus redistributable text/XML samples (official or Apache-2.0 fixtures). OPNsense and CHR are the cheapest to boot in a Linux GitHub Actions job; vJunos is the heaviest.
- **Parse achievable, scan only testable against mocks/recordings:** Cisco IOS/IOS-XE/ASA and PAN-OS. Their fixture bases are the richest of all candidates and OT prevalence (Cisco IE/Stratix) is the highest, so a parse-first Cisco module is high value even though its scan code cannot be exercised against a live free target in CI.
- **Scan achievable from documentation (mock responder in CI), parse blocked on samples:** Moxa NPort/OnCell/MGate (UDP/4800) and Lantronix (UDP/30718). These are the only OT serial-server discovery protocols with publicly known byte layouts; implementing both as PEAT `IPMethod` probes is a small, high-visibility win for OT prevalence (Moxa has the most CISA advisories among candidates).
- **Parse achievable with synthesized fixtures, no soft target:** RUGGEDCOM ROS (`config.csv` CSV, Siemens documents the format and partial-update examples). Scan can use standard SNMP/HTTP/SSH fingerprints plus Modbus register 0x0000, but PEAT lacks a shared Modbus client, so Modbus-based fingerprinting adds scope.
- **Defer unless samples are contributed:** Hirschmann (schema-less XML, undocumented L2 discovery), Sierra Wireless ALEOS (manual-only template export), Westermo, Cradlepoint (well-documented JSON API but no device/fixtures), Digi TransPort (obsolete).
- Library reuse: prefer Apache-2.0/MIT libraries already compatible with PEAT's packaging (textfsm + ntc-templates for `show` output, PyEZ for Junos, pan-os-python for PAN-OS, `requests` for OPNsense/VyOS/RouterOS REST). ciscoconfparse2 is GPLv3 (same as PEAT) but heavyweight; `pyopnsense` and `vymgmt` are stale and not worth adopting.
- CI design implication: keep scan/pull integration tests in a Linux-only, opt-in job that boots one qcow2 (OPNsense nano, VyOS rolling, or CHR raw image) under QEMU/KVM after enabling `/dev/kvm`; Windows/macOS jobs run parse tests only. An SNMP simulator fed with recorded walks (not researched here) would let Cisco/RUGGEDCOM/Hirschmann SNMP fingerprints be tested cross-platform.

### Gaps
- Rockwell Stratix being Cisco IOS-based could not be confirmed from a primary source in this session (Rockwell literature PDF returned HTTP 403; Cisco's Rockwell alliance page does not mention Stratix). Treat as widely reported but unverified here.
- pfSense CE source license (Apache 2.0) and the default `config.xml` fixture were not verified (repository fetches failed).
- OT prevalence figures for pfSense/OPNsense, VyOS, Junos SRX and PAN-OS in utilities/water/municipal networks: no quantitative public source found.
- Sierra Wireless ACEmanager port (9443) and ALEOS SNMP/HTTP fingerprint details not verified; template XML schema not found.
- Not researched at all due to the exhausted search budget: Siemens SCALANCE, RUGGEDCOM ROX II, Phoenix Contact FL SWITCH, Red Lion N-Tron/Sixnet/RAM/SN/Crimson, Advantech EKI, Antaira, InHand, ProSoft, Digi WR/IX and Digi Remote Manager, Ubiquiti EdgeOS/UniFi, Moxa firmware download terms, Hirschmann/RUGGEDCOM CISA advisory counts, Wireshark dissectors for RCDP/HiDiscovery, and SNMP-simulator tooling for CI.
