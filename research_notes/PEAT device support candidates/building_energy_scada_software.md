# Building automation, DER, smart metering, generic Modbus/BACnet/OPC UA fingerprinting, SCADA/HMI/historian software, and IT-OT infrastructure as PEAT module candidates

Research date: 2026-10-31. Scope excludes Ignition, Siemens WinCC, Rockwell FactoryTalk, OpenPLC, CODESYS (covered by other researchers). Note on method: the shared web-search budget was exhausted partway through this task; the remaining findings came from direct fetches of primary pages (GitHub, PyPI, vendor docs, CISA/WaterISAC/nmap). Items marked "not researched" below could not be searched and are listed as gaps rather than guessed.

Maintainer weighting applied throughout (per coordinator clarification): baseline target for a new module is PARSE + SCAN. Ranking weights (1) redistributable sample vendor files to build/test a parser and (2) a free, network-reachable simulator/emulator/soft-runtime answering on real TCP/UDP ports so scan/fingerprint code can be tested in CI without hardware. Pull/push are secondary. Key Question 4 gives the explicit per-candidate parse/scan verdicts.

## Key Question 1: Which standards-based protocols (BACnet, OPC UA, Modbus FC43, SunSpec, Redfish, ONVIF/WS-Discovery, plus 2030.5/OCPP/DLMS) give the broadest multi-vendor coverage per unit of effort, and which have free Docker-able (or natively CI-runnable) simulators?

### Takeaway
Four protocol families have permissively licensed, free, headless simulators that answer on real ports and are suitable for CI today: BACnet/IP (bacnet-stack `bacserv` Dockerfile, GPL-2.0+ with linking exception; YABE DemoServer, MIT; bacpypes3 sample devices, MIT), Modbus/TCP with FC43 identity (pymodbus simulator, BSD-3, pure Python with a configurable `identity` block), OPC UA (Microsoft OPC PLC Docker image, MIT, anonymous access on by default; asyncua pure-Python server, LGPL-3), and Redfish/IPMI (DMTF Redfish Interface Emulator and Mockup Server Docker images, BSD-3; vaporio/ipmi-simulator, GPL-3). ONVIF has a free simulator (OnvifSim, MIT, Linux snap) but weaker CI story; SunSpec has permissive libraries/models but no official simulator; IEEE 2030.5 has two open-source servers but requires TLS client certificates; DLMS libraries are GPL-2.0 dual-licensed with a .NET-only simulator.

### Cited Findings

#### BACnet/IP (multi-vendor building automation)

- PyPI lists bacpypes3 latest version 0.0.110 released September 24, 2026, license expression MIT (but a classifier also says "OSI Approved :: BSD License" — the two fields disagree), Requires-Python >=3.8, author Joel Bender — [PyPI bacpypes3](https://pypi.org/project/bacpypes3/)
- A third-party health scanner (Depscope) rates bacpypes3 57/100 with a maintenance sub-score of 0/20; this conflicts with the September 2026 PyPI release and should be treated as unreliable — [Depscope bacpypes3](https://depscope.dev/pkg/pypi/bacpypes3)
- bacpypes3 samples include discovery scripts (`discover-devices.py`, `whois-tracer.py`, `find-device-by-instance.py`, `find-device-by-address.py`, `who-has.py`), object enumeration (`discover-objects.py`, `discover-objects-csv.py`, `discover-objects-rdf.py`), reads (`read-property.py`, `read-property-multiple-console.py`, `read-batch*.py`, `read-bbmd.py`) and device/server samples (`custom-server.py`, `mini-device-revisited.py`, `mini-device-mcp.py`, `device-object-init-1.py`) — [BACpypes3 samples](https://github.com/JoelBender/BACpypes3/tree/main/samples)
- BAC0 is "Library depending on BACpypes3 (Python 3) to build automation script for BACnet applications", licensed LGPLv3, Python 3.10+, 246 stars, 1,258 commits; README says it can "browse a BACnet network" and "read properties from BACnet devices, and write to them" — [GitHub ChristianTremblay/BAC0](https://github.com/ChristianTremblay/BAC0)
- BAC0 latest PyPI release is 2026.7.25 (July 26, 2026), LGPL-3.0, "3.10 and over" — [PyPI BAC0](https://pypi.org/project/BAC0/)
- bacnet-stack (Steve Karg) core code is "SPDX-License-Identifier: GPL-2.0-or-later WITH GCC-exception-2.0"; skeleton/example/template files are MIT or Apache-2.0; the exception lets the library be linked into proprietary code; "dozens of sample applications" including server, gateway, router and MS/TP apps; CI builds on Ubuntu, Windows and macOS; BACnet/IPv4 default plus IPv6, Ethernet, ARCNET, MS/TP — [GitHub bacnet-stack/bacnet-stack](https://github.com/bacnet-stack/bacnet-stack)

### Inferences
- Breadth per unit of effort, highest to lowest: (1) BACnet/IP — one module covers every BACnet vendor (JCI, Honeywell, Siemens, Trane, Carrier/ALC, Distech, Delta, KMC) because device identity properties are standardized, and three independent free simulators exist (bacnet-stack bacserv in Docker, YABE DemoServer on Windows/Mono, bacpypes3 mini-device in pure Python); (2) OPC UA — embedded in most modern PLCs/HMIs/historians, with an MIT Docker simulator that allows anonymous reads by default; (3) Modbus FC43 — PEAT already has Modbus code, and the pymodbus simulator exposes a configurable identity block so a FC43 fingerprint can be tested without Docker on all three CI OSes; (4) Redfish/IPMI — trivially testable in CI but generic IT.
- CI portability: bacpypes3, asyncua, pymodbus and the DMTF Python emulator are pure Python and therefore run natively on Linux, Windows and macOS GitHub runners without Docker; bacnet-stack also builds natively on all three OSes per its own CI, so a native `bacserv` binary is an alternative to the Docker image where Linux containers are unavailable (not verified for GitHub Actions specifically).
- BACnet Who-Is is UDP broadcast; inside Docker bridge networking the scan would need unicast Who-Is to the container IP or `--network host` (inference from protocol behavior; not tested here).
- SunSpec scan testing can be built on the pymodbus simulator by loading the Apache-2.0 JSON model definitions into holding registers (common model 1 at the well-known base plus 7xx models) — feasible but requires PEAT to author the register map; no ready-made SunSpec simulator image was found.
- IEEE 2030.5 servers require mutual TLS with device certificates, so a PEAT "scan" would be limited to TLS-level fingerprinting unless PEAT provisions a client cert; this makes 2030.5 a poor fit for a generic unauthenticated scan.
- OCPP chargers are WebSocket clients of a central system, so a network scanner cannot fingerprint a charger over OCPP; OCPP is a weak scan candidate regardless of simulator availability.
- The Gurux GPL-2.0 marking (without visible "or later") may be license-incompatible with PEAT's GPLv3 for code linking; confirm the exact text before adopting. The .NET-only simulator also complicates CI compared with pure-Python options.
- The bacpypes3 PyPI license-field inconsistency (MIT expression vs BSD classifier) is a trivial legal caveat; both are permissive and GPLv3-compatible.

- No IEEE 2030.5 server attributable to EPRI was found; EPRI involvement is unconfirmed.

- Inverter vendor local APIs (SMA, Fronius Solar API, SolarEdge, Enphase Envoy) were not researched (search budget).

## Key Question 2: Which SCADA/HMI/OPC/BAS products have free or long-trial software with documented, text-based project/config exports suitable for parse-only modules (Kepware JSON, Niagara .bog/.dist, VTScada, AVEVA, GE, open-source SCADA)?

### Takeaway
Kepware Server (KEPServerEX) is the strongest parse candidate: a free demo with unlimited tags that runs in 2-hour restartable windows, a documented human-editable JSON project export (since 6.0) and a documented REST Configuration API returning the same JSON, with a long CISA advisory history and rebrands (GE IGS, Software Toolbox TOP Server) that inherit the format. VTScadaLIGHT (free up to 50 I/O) stores applications as text `.SRC`, INI-style `Settings.*` and `Servers.XML`, making a parser feasible from self-generated fixtures. AVEVA InTouch has a free fully functional trial and `.aaPKG`/XML graphics exports but the package internals were not verified. Niagara is the highest-value BAS target (Fox identity handshake fully documented in nmap; `.dist` backups contain `config.bog`) but no free Workbench/station was found and the bog container format and 4.15 bog encryption were not verified from Tridium sources. GE iFIX/CIMPLICITY have free 2-hour trials but project formats were not determined.

#### Kepware Server / KEPServerEX (PTC)
- PTC: "KEPServerEX is now Kepware Server"; the demo "will run for 2 hours at a time", can be restarted by stopping and starting the application, and "Channel, Device, and Tag counts are unlimited"; download requires a form — [PTC demo download](https://ptc.com/products/kepware/KEPServerEX/demo-download); [PTC Kepware Server demo](https://www.ptc.com/en/products/kepware/kepware-server/demo-download)
- PTC 6.0 release notes: added "exporting project files to a human-editable JSON format, which replaces the XML format previously used for that purpose" to support the Configuration API Service — [PTC What's New 6.0.2107.0](https://support.ptc.com/help/kepware/kepserverex/en/kepware/kepserverex/whats_new/whats_new_6_0_2107_0.html)
- Export path: Configuration client File > Save As, file type JSON; "Project File Encryption" is on by default and blocks JSON export (disable under Project Properties | General); projects using the Security Policies plug-in can only be saved as `.opf` and must be exported via the Configuration API; 5.x cannot save JSON — [Cybus migration guide](https://docs.cybus.io/guides/migration/migrating-from-kepware-kepserverex)
- JSON structure: top-level `project` with `servermain.PROJECT_TITLE` and `channels[]`; channel keys `common.ALLTYPES_NAME`, `servermain.MULTIPLE_TYPES_DEVICE_DRIVER`, `devices[]`; device keys `common.ALLTYPES_NAME`, `servermain.DEVICE_ID_STRING`, `servermain.DEVICE_SCAN_MODE_RATE_MS`, driver-specific keys like `modbus_ethernet.DEVICE_ETHERNET_PORT_NUMBER`, `tags[]`; tag keys `servermain.TAG_ADDRESS`, `servermain.TAG_DATA_TYPE`, `servermain.TAG_READ_WRITE_ACCESS`, `servermain.TAG_SCAN_RATE_MILLISECONDS`; plug-ins under `_datalogger`, `_iot_gateway` — [Cybus migration guide](https://docs.cybus.io/guides/migration/migrating-from-kepware-kepserverex)
- Configuration API: enable under Administration > Settings > Configuration API Service; HTTP 57412 / HTTPS 57512; `GET /config/v1/project?content=serialize` returns the whole project as JSON; HTTP basic auth with a server user (e.g., Administrator); self-signed cert by default; API documentation is served locally at 127.0.0.1:57412/config — [Cybus migration guide](https://docs.cybus.io/guides/migration/migrating-from-kepware-kepserverex); [Kepware Configuration API Easy Guide (Scribd copy)](https://www.scribd.com/document/495138516/configuration-api-made-easy)

### Inferences
- Shortlist by the maintainer's weighting (fixtures first, then port-answering simulator): (1) Kepware Server (parse JSON + API scan; fixtures self-authored; Windows-only live target); (2) BACnet/IP generic (best scan story with three permissive simulators incl. Docker and pure Python; parse n/a); (3) Modbus FC43 generic (cheapest scan add-on to existing PEAT Modbus; parse n/a); (4) OPC UA generic (MIT Docker simulator with anonymous access; parse n/a); (5) VTScada (text fixtures via free VTScadaLIGHT; scan only on Windows); (6) Redfish/IPMI (trivial CI, public JSON mockups as fixtures, but generic IT); (7) Niagara (highest BAS value; scan implementable from nmap grammar with a self-written mock; parse blocked on fixtures); (8) SunSpec (mission-aligned; requires building a simulator register map); (9) ONVIF (Linux-only simulator); (10) AVEVA/GE (free trials, formats unverified); (11) 2030.5/OCPP/DLMS/water RTUs/APC/Axis (low feasibility or low scan value).
- GPL-licensed simulators (bacnet-stack, ipmi-simulator) are fine as CI *test targets* since PEAT does not link against them; only client libraries PEAT imports (bacpypes3 MIT, pymodbus BSD-3, asyncua LGPL-3, pysunspec2 Apache-2.0, onveef Apache-2.0, Gurux GPL-2.0) affect PEAT's GPLv3 compatibility — all are compatible except possibly Gurux if it is GPL-2.0-only.

### Gaps
- No candidate in this scope was found with vendor-published, explicitly redistributable sample config/backup files; all parse fixtures would be self-generated (Kepware, VTScada, AVEVA, GE) or taken from standards bodies' mockups (DMTF). Redistribution terms for DMTF mockups, PTC doc samples and Trihedral user-authored apps were not verified.
- Feasibility of running Linux Docker containers, snapd (for OnvifSim), or form-gated Windows demos (Kepware, VTScadaLIGHT, InTouch, iFIX) on GitHub-hosted Windows/macOS runners was not verified in this research.
