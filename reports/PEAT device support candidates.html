Thirteen candidates let PEAT reach its PARSE-plus-SCAN baseline without buying hardware, and two lead the field. A generic IEC 61850 IED module (SCL XML parse plus MMS nameplate scan) is the only candidate with fully redistributable public fixtures (libiec61850's GPLv3 ICD/CID files, OpenSCD's Apache-2.0 SCDs, the IEC XSDs under the attribution-only CC-EULA) and a free headless server for CI, and it covers ABB/Hitachi, Siemens SIPROTEC 5, GE, SEL, Schneider and Beckwith relays in one module. A Siemens S7 module has the best-verified scan target of any candidate: the pure-Python, MIT-licensed python-snap7 3.x server and the s7commplus emulator pip-install on Linux, Windows and macOS runners, run on unprivileged ports, and answer exactly the SZL/identity queries a fingerprint issues — and the August 2026 NSA/CISA AA26-231A advisory on adversary reconnaissance of S7 PLCs gives it the strongest security mandate. Behind them, three cheap extensions (CompactLogix via the ControlLogix module tested against cpppo/Conpot, OpenPLC v3 via the v4 module in Docker, M580/Quantum via the M340 UMAS code) and new modules for Unitronics Vision (documented PCOM protocol, ZIP .vlp projects, the AA23-335A water-sector campaign), AutomationDirect CLICK/Do-more, CODESYS V3 (one container fingerprints WAGO, Schneider M241–M262, Festo, ABB and Eaton runtimes), Ignition, and three network OSes that boot free under KVM (OPNsense/pfSense, MikroTik CHR, VyOS) all clear both bars. Standards-based scan primitives — Modbus FC43 via the pymodbus simulator, BACnet via bacpypes3/bacnet-stack, OPC UA via Microsoft's OPC PLC container, DNP3 Group 0 via opendnp3 or Sandia's bennu — multiply vendor coverage per line of code but have no file to parse. The recurring weakness across every vendor cluster is fixtures, not formats: open XML/text formats exist for Siemens, Beckhoff, Kepware, VTScada, SCALANCE and RUGGEDCOM, yet almost no vendor publishes redistributable samples, so most parse fixtures must be self-generated with free or trial engineering software (often Windows-only) and committed as PEAT-authored content. The legal tripwires are concrete and avoidable: Step Function I/O's DNP3 library forbids use as a test oracle, GPLv2-only Omron and Gurux libraries cannot link into GPLv3 PEAT, s7commplus bundles reverse-engineered Siemens key material, and the Rockwell, Schneider, Siemens and CODESYS EULAs prohibit reverse engineering and gate downloads behind accounts.

Pure-Python emulators and open XML decide the ranking

The maintainer's two weights — (1) redistributable sample files to build and test a parser and (2) a free, network-reachable simulator that answers on real TCP/UDP ports so a scan can run in CI — sort the field cleanly, because the two properties are almost never found together in one vendor. Pure-Python simulators (python-snap7, s7commplus, pymodbus, bacpypes3, asyncua, pyclickplc's ClickServer) are the gold standard for criterion 2 because they run on all three GitHub Actions runner OSes without Docker or KVM; official Docker images (OpenPLC, Ignition, Conpot, OPC PLC, bacnet-stack, CODESYS Virtual Control) are a half-step down because they confine scan tests to the Linux job; KVM-booted network OS images (OPNsense, VyOS, CHR, vJunos) are another half-step down because they need /dev/kvm, which GitHub exposed on 2-vCPU hosted Linux runners only in April 2024 (GitHub Changelog); Windows-only GUI simulators (Control Expert, Logix Echo, PLCSIM Advanced, Do-more DMSim, Kepware demo) are usable for manual regression but not unattended CI. For criterion 1, the ideal is a permissively licensed public corpus (IEC 61850 SCL, ntc-templates, VyOS smoketests, python-comtrade, Beckhoff's 0BSD repos); next best is a free IDE that lets PEAT developers author and commit their own fixtures with no redistribution question (VisiLogic, CLICK, CCW Standard, Kepware demo, VTScadaLIGHT, OPNsense/CHR/VyOS VMs); weakest is a format whose only samples are vendor-copyrighted demos or require paid or 21-to-30-day trial software (Schneider .xef, TIA Openness XML, Studio 5000 L5X beyond pycomm3's test file).

Four patterns in the table drive the rest of this report. First, every candidate in ranks 1–13 passes both bars, but only ranks 1, 3, 4, 9 and 11 do so with a public fixture corpus; the others rely on PEAT-authored fixtures generated in free software, which is legally cleaner than copying vendor samples but means a Windows session is on the critical path for Siemens, Rockwell, Unitronics, AutomationDirect and CODESYS. Second, the standards rows (14–16, 19, 20) are not modules in PEAT's sense but primitives that make a dozen vendor modules cheaper; FC43 alone upgrades scan coverage for M580, SCADAPack, ION meters, Eaton easyE4, Weintek, Horner and the AutomationDirect families. Third, the network-infrastructure rows (9–11) are the only candidates whose free soft target is the actual vendor OS, not an emulator, so scan fidelity is perfect — at the cost of Linux-only KVM jobs. Fourth, the parse-only rows (17, 18, 20, 23–25) carry the richest fixture bases of all but cannot be scan-tested in CI; they are worth doing as parse modules while scan code waits for hardware or donated captures.

Tier 1 controllers: S7, IEC 61850, AutomationDirect, Unitronics and CODESYS

IEC 61850 generic IED (rank 1)

Documentation quality is the best of any candidate because the format is an international standard: the IEC 61850-6 SCL XSDs are republished by LF Energy's CoMPAS project under the IEC Code Components End-User Licence, which permits redistribution provided the copyright notice is retained and each component is attributed to IEC and the standard it derives from (compas-scl-xsd; IEC CC-EULA). Redistributable fixtures exist in three places: libiec61850 ships simpleIO_direct_control.icd and .cid in its GPLv3 repository, with LLN0.NamPlt instantiated as vendor "MZ Automation", swRev "1.3.0" (server_example_basic_io; ICD file); OpenSCD's Apache-2.0 repository holds at least seven .scd test files including valid2003.scd, valid2007B.scd and valid2007B4.scd (open-scd testfiles); and KIT published a 2025 dataset of SCDs built with RTDS Configurator, SEL AcSELerator and OMICRON IEDScout, but under CC BY-NC 4.0, so it is suitable for local testing only (KITopen).

The simulator story is equally strong. libiec61850 (GPLv3 with commercial option) provides 18 server examples including basic I/O, config-file, file-services, password-auth and TLS variants that build with CMake on Linux, Windows and macOS (libiec61850 README; examples). Three Python libraries compete for the client role: iec61850 0.15.2 (uploaded 2026-10-30, "MIT OR Apache-2.0", Python ≥3.11) offers load_scl() returning an IED inventory, an async MMS client, and an IedServer.from_scl server — but is classified Pre-Alpha (PyPI iec61850); `pyiec61850-ng` 1.6.1.10 (GPLv3, Python 3.9–3.14) exposes "server identity, logical device and node discovery" with Linux and Windows wheels but no macOS wheels and a single maintainer who calls it experimental (PyPI pyiec61850-ng); `py61850` 0.6.0 ships mms-scan but is AGPL-3.0 and requires Python 3.13, which conflicts with PEAT's >=3.11,<3.14 floor and would pull the combined work toward AGPL for network use (PyPI py61850). Sandia's own bennu builds an IEC 61850 GOOSE library but no MMS server, so it is not a scan target (bennu iec61850 CMakeLists).

Fit with PEAT is excellent on the parse side (lxml is already used for L5X, RTAC and M340 XML) and moderate on the scan side (MMS over ISO-TCP on port 102 is a new protocol, and it shares the port with S7comm, so the module must disambiguate an ISO-TCP peer that answers MMS Initiate from one that answers S7comm 0x32). Security relevance is high: the module would yield IED name, manufacturer, configVersion, per-AccessPoint IP/subnet/gateway, logical-device inventory and GOOSE/SV control blocks for every 61850 vendor, including GE UR relays (CISA ICSA-21-075-02, nine CVEs, overall CVSS 9.8 (CISA)) and Hitachi Relion 670/650 (ICSA-21-336-05, CVSS 8.1/8.9 (CISA)). Effort: SCL parse small (days to two weeks); MMS nameplate scan medium (two to four weeks), with the main risk being which Python MMS client to standardize on.

Siemens SIMATIC S7-300/400 and S7-1200/1500 (rank 2)

This candidate has the single best-verified CI target in the research. python-snap7 3.3.1 (released 2026-10-28, MIT, Python ≥3.10) is a pure-Python reimplementation with a py3-none-any wheel and no native dependency (PyPI); its `snap7.server.Server` "emulates a Siemens S7 PLC for testing" and starts on any TCP port (Server API). The research team installed it on Linux and confirmed that Server().start(tcp_port=11102) answered get_cpu_info() with module CPU 315-2 PN/DP, get_order_code() with 6ES7 315-2EH14-0AB0 V3.3.0, get_protection(), get_cpu_state(), get_plc_datetime(), list_blocks(), and SZL IDs 0x0000/0x0011/0x001C/0x0131/0x0232 — exactly the queries a fingerprint issues — while full_upload(OB,1) failed with "block not found", so logic pull is only partially testable. For the newer families, s7commplus 0.3.0 (2026-10-20, MIT, Python ≥3.10) is a pure-Python S7CommPlus client with "a server emulator for testing" covering protocol V1, V2 (TLS) and V3, and a 105-entry DEVICE_NAMES table that maps order numbers to models; the emulator reports 6ES7 215-1AG40-0XB0 V4.2 (a CPU 1215C) during the connect handshake (PyPI s7commplus; GitHub). Conpot (GPL-2.0) is an independent second responder in Docker whose s7comm.toml exposes configurable SZL 0x1C identity strings on port 10201 (conpot s7comm.toml), useful to prove PEAT's fingerprinting does not overfit snap7's constants.

Documentation is adequate for classic S7comm (Wireshark's wiki hosts six sample pcaps and a "partially functional" dissector (Wireshark S7comm); Snap7's compatibility matrix states which operations S7-1200/1500 refuse — block directory and upload are not available via classic S7 (Snap7 client)) and weaker for S7comm-plus, which is proprietary and reverse-engineered (the Rogue7 team at Black Hat 2019 described session-key exchange, message integrity and a "stealth program injection" attack (Rogue7 whitepaper)). The officially documented pull path for S7-1500 is the HTTPS JSON-RPC Web API at /api/jsonrpc (Api.Login, PlcProgram.Browse/Read, Modules.ReadIdentificationMaintenance, backup download) with a Siemens-published MIT .NET client (S7-1500 web server manual; siemens/simatic-s7-webserver-api), but no free emulator exposes it; S7-PLCSIM Advanced (Windows, 21-day trial) is the only simulator with a working web server (PLCSIM Advanced manual), so Web API tests would use recorded JSON fixtures.

Parse is the weak side. TIA Portal Openness documents XML export of blocks, tag tables, UDTs, HMI screens and AutomationML hardware (TIA Openness V20 manual), and simaticml-decoder (Python ≥3.11) proves LAD/FBD-to-SCL conversion is tractable, but it ships no sample XML and states its probe files are "not a distributable fixture corpus" (PyPI simaticml-decoder). No redistributable SimaticML corpus was found anywhere; fixtures must be generated with the 21-day TIA Portal V20 trial on Windows (Siemens forum), and the trial EULA was not reviewed. Fit: PEAT's pyproject.toml already carries a commented python-snap7==0.11 pin from a pre-rewrite era; a new module should target 3.x and drop the C-library dependency. Security relevance is the highest in this report: AA26-231A (Aug 19, 2026; NSA, CISA, FBI, DOE, EPA) describes adversaries using python-snap7 and snap7.dll for "CPU property enumeration" against S7-200/300/400/1200/1500 in energy, water and chemical sectors, and its mitigations — inventory all S7 PLCs, verify firmware against a gold copy, review protection levels — read as PEAT's mission statement (CISA AA26-231A). That same fact means PEAT's S7 module will look like adversary tooling on the wire; it should be documented for defenders. Legal caveat: s7commplus probes "a bounded set of bundled keys" derived from HarpoS7 (MIT) for older PLCs unless allow_legacy_key_fallback=False; treat S7comm-plus as scan/identity only until counsel reviews. Effort: scan small; identity/SZL pull small-medium; SimaticML/.scl parse medium.

AutomationDirect CLICK, Do-more and Productivity (rank 5)

AutomationDirect matters because of US small-utility ubiquity and a fresh advisory stream: CLICK PLUS ICSA-25-266-01 lists seven CVEs including a hard-coded AES key and CVSS v4 8.7 PRNG and RSA flaws (CISA), and ICSA-26-022-02 (Jan 2026) reports that CLICK PLUS project files store passwords with weak encoding or in plaintext so "an attacker with access to the project file could use exposed credentials" (CISA) — which makes a .ckp parser a high-value credential extractor for PEAT's user model, if the format can be understood. The tooling is unusually good: pyclickplc 0.4.1 (MIT, Oct 2026) is an async Modbus/TCP client plus a ClickServer that "simulates a CLICK PLC over Modbus TCP" for "development and testing without hardware", and reads the CLICK software's open nickname CSV and DataView CDV exports (PyPI pyclickplc; GitHub). For Do-more, a long-time community expert reports that the Do-more Designer simulator "just listens on port 28784 (0x7070) and does not specifically bind to an adapter" and that a Modbus/TCP HMI connected to it via the PC's IP (AutomationDirect Community), making it the one free vendor simulator in this study that answers vendor-ish traffic on a NIC — but only on a Windows runner, and its silent-install behaviour is unverified. The Productivity Suite simulator (3.8+) exposes Modbus/TCP only (AutomationDirect Community). Fit: PEAT's Modbus code is reusable; CLICK PLUS's native KOPS/KOPR session protocol and Do-more's native protocol are proprietary (large, EULA-risky). Legal: no AutomationDirect EULA text was retrievable; check before reverse-engineering .ckp/.dmd. Effort: CSV/CDV parse small, .ckp medium; Modbus-based scan small-medium.

Unitronics Vision / Samba (rank 6)

Unitronics is the highest-signal small-PLC target for Sandia's mission because it is tied to a confirmed nation-state campaign: AA23-335A documents IRGC-affiliated "CyberAv3ngers" compromising at least 75 Unitronics Vision devices, at least 34 in the US water and wastewater sector, by brute-forcing internet-exposed TCP 20256, erasing ladder logic and defacing HMIs (CISA AA23-335A). The protocol is officially documented: Unitronics' PCOM specification defines ASCII and binary framing, the 6-byte TCP header (transaction ID, protocol 101/102, length), and the ID/UG/GF-style identity commands (Unitronics PCOM PDF). Reusable code is plentiful and GPLv3-compatible: pcom on PyPI is MIT (Ethernet only, v0.11 from 2022) (PyPI pcom); Claroty's PCOM-Tools provide a modular client with opcodes for Get PLC Name (0x0C), Read Operand (0x4D) and the ID/UG/GF identity strings (claroty/PCOM-Tools); Praetorian's Apache-2.0 Nerva fingerprinter documents the PCOM/TCP probe on 20256 (nerva). No vendor simulator exists, but the protocol is simple enough that a mock PCOM server answering ID/UG/GF is a small, cross-platform CI fixture.

File format: ZDI-16-375 states the VisiLogic .vlp project "uses the zip file format" (ZDI-16-375), and VisiLogic itself is free ("All Unitronics software & utilities—plus updates—provided at no charge", latest 9.9.01 (Unitronics VisiLogic)), so PEAT can author its own .vlp fixtures on Windows; the encoding of the inner ZIP members was not inspected and is the parse risk. Fit: PCOM/TCP is a new protocol driver but tiny. Legal: read the VisiLogic EULA before shipping a .vlp parser; do not redistribute vendor sample projects. Effort: parse medium; scan small-medium; pull of PLC name, unit ID and firmware via PCOM small once a mock exists.

CODESYS V3 generic runtime (rank 7)

One CODESYS module fingerprints a very large installed base: CODESYS claims about 1,000 device types from more than 500 manufacturers (devices.codesys.com), Microsoft tested its CoDe16 vulnerabilities on Schneider Modicon TM251 and WAGO PFC200 (Microsoft Security Blog), and CISA's ICSA-25-093-03 covers ABB ACS880 drives "Containing CODESYS RTS" (CISA). The simulator is official: the CODESYS Virtual Control SL datasheet lists "Demo-/Test-Mode: yes, 2 hours", delivery as a Debian package and a container image (x86_64/ARM64, Docker or Podman, kernel ≥6.1), and "Without a license, each controller runs in demo mode for two hours" (Virtual Control SL datasheet); Intel's ECI documentation confirms the Linux runtime "is free to use without a license" but stops after two hours and that the store download "requires an account" (Intel ECI). A two-hour limit is harmless for a CI job, but the account-gated EULA means the CI pipeline must fetch the package with credentials or use a private image rather than publishing one.

Protocol documentation is unofficial but sufficient: Microsoft's MIT-licensed CoDe16 repository contains a Wireshark dissector for the CODESYS V3 protocol and an "active tool to extract the CODESYS V3 runtime version of devices" (archived June 2026, still cloneable) (microsoft/CoDe16); Kaspersky's 2019 analysis maps the four-layer PDU (block driver, datagram, channel, services) and service IDs such as CmpDevice 0x1 and CmpApp 0x2 (Kaspersky PDF); Nozomi documents a UDP-only discovery on ports 1740–1743 returning device_name, node_name, serial_number, vendor_name and version (Nozomi). File formats: CODESYS documents two exports — a native XML *.export "fully compatible with the CODESYS project format" and PLCopen XML, which "defines a subset" (CODESYS Help) — and PLCopen TC6 maps directly onto PEAT's existing PLCopen generator and the Beremiz-style plc.xml fixture already in the repo. The .project container is undocumented; do not attempt it. Pull of logic (CmpFileTransfer, CmpApp) requires the authenticated, partially encrypted channel and raises EULA questions, so scope pull to web/OPC UA/SSH side services. Effort: scan medium (two to four weeks including a packet capture against the container to pin the 72-byte discovery frame); parse small-medium.

Cheap extensions reuse ControlLogix, OpenPLC, M340 and EDS code

CompactLogix / GuardLogix via the ControlLogix module (rank 3)

Rockwell's own reference manual requires any third-party communications software for "a ControlLogix or CompactLogix controller" to follow the same Logix 5000 Data Access manual 1756-PM020 (Logix 5000 reference manual), and pycomm3 and pylogix both treat CompactLogix identically to ControlLogix (pycomm3; pylogix). The L5X schema is shared, so PEAT's parser works today; pycomm3's MIT repository contains an L5X test export usable as a fixture, though whether it came from a CompactLogix was not checked. For scan, cpppo's enip_server answers broadcast ListIdentity and lets cpppo.cfg override the Identity Object's Product Name (dual GPLv3/proprietary; 5.2.5 released Feb 2025; PyPI classifiers list only generic Python 2/3, so a 3.11–3.13 smoke test is required) (cpppo GitHub; PyPI), and Conpot's Docker image ships an ENIP identity of VendorId 1, DeviceType 14, ProductCode 90, ProductName "1756-L61/B LOGIX5561" on port 44818 (conpot enip.toml). That Conpot identity is a useful negative test: product code 90 is in PEAT's MLX_PRODUCT_CODES (MicroLogix 1400 or 1794-AENT) in peat/modules/rockwell/clx_const.py, so PEAT would brand it "MicroLogix" — an argument for the (vendor, device_type, product_code) lookup that clx_const.py and ab_scan.py already carry as TODOs. Caveats: Conpot's ENIP is mode = "tcp", so UDP broadcast ListIdentity is likely unanswered; neither emulator supports connected messaging, program upload or PCCC, so pull/push remain untestable without FactoryTalk Logix Echo (30-day trial requiring Studio 5000 (Rockwell blog)) or hardware; CompactLogix 5380/5480 use a different slot/path model than 1756 backplanes and enforce ANSI Extended Symbolic 0x91 segments, so ab_scan.py's chassis_size=8 enumeration needs a per-family strategy. Security relevance: SD1693/CVE-2024-6077 is a CIP Security Object DoS on CompactLogix 5380 requiring factory reset (Rockwell SD1693). Effort: small.

OpenPLC Runtime v3 via the v4 module (rank 4)

OpenPLC v3 is archived and "has reached End of Life", but it remains buildable: ./install.sh docker or docker build -t openplc:v3 . then -p 8080:8080 (thiagoralves/OpenPLC_v3). Its webserver.py is a Flask app on 0.0.0.0:8080 with a second Flask app on 8443 exposing a /api blueprint (start-plc, stop-plc, status, upload-file), plaintext password comparison, and routes /programs, /users, /settings, /hardware, /runtime_logs, /upload-program, /compile-program (webserver.py) — a direct adaptation of PEAT's requests-based openplcv4.py, whose CI already runs ghcr.io/autonomy-logic/openplc-runtime:latest in .github/workflows/tests-container.yml. PEAT's fixture tests/modules/openplc/data_files/Relay_Blink_PLC.zip already contains a PLCopen TC6 v2.01 plc.xml. Security relevance: an NVD keyword search returns 26 OpenPLC CVEs including CVE-2024-34026 (EtherNet/IP stack overflow RCE, 9.8), CVE-2025-1066 (arbitrary upload, 9.8) and CVE-2026-28205 (API auth bypass, 9.8) (NVD). Licence: GPL-3.0 runtime, compatible. Effort: small (days) for parse, scan, pull and push.

M580 / Quantum / Premium / Momentum via the M340 UMAS code (rank 13)

Kaspersky's UMAS analysis confirms M340 and M580 share the protocol (Modbus function 0x5A, one-byte session key, UMAS function code), with differences only in fix versions (M340 3.50, M580 4.10) and in M580 4.x "secure UMAS" authentication (Kaspersky ICS-CERT); PEAT's umas_codes.py/umas_packets.py therefore extend with identity/CPU-model decoding per family. The parse path is Control Expert's .xef export, "an XML source format" containing I/O configuration, sections, DFB types, DDTs and variables, documented in the Operating Modes manual (se.com FAQ000259996); demo `.xef` files (Quantum and Premium) ship with Control Expert and are attached to a public FAQ (se.com FA364303), but they are Schneider-copyrighted, so PEAT should commit a hand-authored minimal XEF instead. The highest-fidelity simulator is Control Expert's built-in PLC simulator: Cisco Talos documented that it "opens 0.0.0.0:502 on the host, allowing for any supported UMAS command" including the TAKE_PLC_RESERVATION sequence (Talos TALOS-2019-0771), and Control Expert "comes with a 30 day trial license" (se.com FA369070) — a Windows GUI, so manual regression only, and whether current V15/V16 versions still expose unauthenticated UMAS was not verified. For CI, the pymodbus simulator answering FC43 with Schneider-like strings (BMENOC modules "return vendor name, product name, and version through function code 43" (se.com FA406524)) or a PEAT-built UMAS responder covers scan. Effort: small-medium.

Micro800 and Connected Components Workbench (rank 12)

CCW Standard is free from Rockwell's PCDC and "includes a demo version of Micro800 Simulator" needing no activation (Rockwell store); the simulated controller is `2080-LC50-48QWB-SIM` (The Automation Blog), and a forum report says the free version drops to Program mode after 10 minutes. The project format is almost certainly XML — CVE-2022-1018 is an XML external entity flaw in CCW ≤12.00 (wiz.io) — but no primary source confirms the .ccwsln/.ccwarc/.acproj structure, so one Windows session to generate and inspect a project is the gating step. Scan reuses the cpppo/Conpot identity emulation of rank 3 with Micro8xx codes and no backplane path (pylogix: "you must set the Micro800 flag since the path is different" (pylogix)). Security relevance is fresh and critical: ICSA-25-226-25 (Aug 2025) covers Micro820/850/870 with Azure RTOS CVEs at CVSS 9.8 and CVE-2025-7693, a malformed CIP Forward Close that faults the controller (CISA). Effort: parse medium (after format inspection); scan small.

EDS-based identity enrichment (fleet-wide)

EDS files are plain ASCII, distributed free via PCDC (Rockwell product downloads), and are the canonical source for vendor/device-type/product-code-to-name mappings that PEAT's clx_const.py hard-codes today; controllogix.py already looks for *.eds on EN2T/EWEB FTP shares. Because EDS redistribution terms were not found, PEAT should ship a derived lookup table rather than the files. Effort: small once a bulk EDS source is obtained; it directly improves scan accuracy for PowerFlex, Kinetix, POINT/FLEX I/O and switches as well as controllers.

Network infrastructure: OPNsense, MikroTik and VyOS boot free under KVM

These three are the only candidates whose free soft target is the vendor's real operating system. GitHub's hosted 2-vCPU Linux runners have exposed KVM since April 2024 (the example workflow adds a 99-kvm4all.rules udev rule) (GitHub Changelog), so an opt-in Linux integration job can boot one qcow2 and run scan and pull tests against it, while Windows/macOS jobs run parse tests only.

OPNsense (rank 10) is BSD-2-Clause (LICENSE), downloads anonymously from community mirrors as dvd/vga/serial/nano images with default credentials root/opnsense (install docs), and exposes a documented REST API at https://<host>/api/<module>/<controller>/<command> authenticated with a key/secret pair (API docs). The nano image is pre-installed, avoiding the interactive installer, and a community KVM-in-Docker image (koichirok/docker-opnsense, needs /dev/kvm, stale by a year) shows the pattern (Docker Hub). The only official fixture is a partial config.xml.sample with <system>, <interfaces>, <nat> and an <OPNsense> model section but no <dhcpd>, <snmpd> or <syslog> (config.xml.sample); full fixtures come from the VM. pfSense CE shares the config.xml lineage (Netgate documents it as "all configuration settings including settings for packages" without a schema (Netgate docs)) but its download now routes through Netgate's store/installer (pfsense.org/download), so treat pfSense as a parser sibling tested on the OPNsense VM. Fit: HTTPS and SSH are in PEAT; the Fortinet module (~1,660 lines) is the effort yardstick. pyopnsense (GPLv3) is stale since 2023 and not worth adopting. Effort: small-medium. OT prevalence of either firewall was not quantified.

MikroTik RouterOS CHR (rank 9) is the strongest incident-relevance story among network candidates: CISA warned in September 2026 of CVE-2026-84411, a CVSS 9.8 pre-authentication RCE in RouterOS web management before 7.24 (BleepingComputer), and MikroTik routers underpin the Mēris botnet and a reported ~230,000-router botnet-as-a-service. The CHR Free licence "runs indefinitely" with only a 1 Mbps per-interface cap, ships RAW/VMDK/VHDX/VDI images, and supports QEMU/KVM (CHR docs; CHR licensing). The REST API (RouterOS ≥7.1) uses HTTP basic auth with console credentials and POST /rest/export returns the configuration (REST API docs); `/export` produces a plain-text .rsc of add/set commands (omits passwords, certificates and SSH keys) (Configuration Management). ntc-templates (Apache-2.0) ships about 47 mikrotik_routeros TextFSM templates with .raw fixtures (index; LICENSE). Effort: small-medium.

VyOS (rank 11) has the cleanest fixture base of the three — 52 smoketest config.boot files in vyos-1x (smoketest configs) — free rolling ISOs as GitHub releases (LTS binaries are subscriber-only; "VyOS Stream" is free) (vyos.net/get), and an HTTP API whose /retrieve and /show endpoints return the structured or flat-set configuration (VyOS HTTP API). It ranks last in Tier 1 only because no OT prevalence or advisory data was found. Effort: small.

Juniper vJunos is legally clean (free, non-production, no time limit, EULA at download (Juniper vJunos labs)) with Apache-2.0 fixtures (ntc-templates juniper_junos, Batfish) and PyEZ, but needs about 4 vCPU/5 GB, takes ~15 minutes to boot and "cannot be used in deployments launched from within a VM" per containerlab (containerlab vJunos-switch) — a nightly-job candidate at best.

Cisco IOS/IOS-XE/ASA (rank 23), including Rockwell Stratix and Catalyst IE rugged switches, has the richest fixture base of any candidate (ntc-templates cisco_ios/cisco_asa/cisco_nxos/cisco_xr and Batfish grammar tests, all Apache-2.0 (Batfish supported devices)) and the highest OT prevalence, but no legal free CI target: CML-Free allows 5 nodes on VMware or bare metal and "the Cisco VM images provided for download are only licensed for use within Cisco Modeling Labs" (CML-Free docs). Note that ntc-templates deliberately has no whole show running-config template for IOS, so PEAT would write its own indent parser (as the Fortinet module does) or adopt ciscoconfparse2, which is GPLv3 and compatible but heavyweight (PyPI ciscoconfparse2). Stratix is security-relevant now — SD1749/CVE-2025-20352 is a KEV-listed Cisco IOS SNMP RCE/DoS affecting Stratix 5700/5400/5410/5200/5800 (Rockwell SD1749) — but its Cisco lineage could not be confirmed from a primary source this session. A parse-first peat/modules/cisco with Stratix detection strings is the realistic design.

Moxa and Lantronix (rank 21) are scan-only wins. Metasploit's moxa_discover sends 8 bytes 01 00 00 08 00 00 00 00 to UDP/4800 and expects a 24-byte reply starting 0x81 with the Moxa OUI 00:90:e8 at bytes 14–16 (moxa_discover.rb); a 2019 Habr write-up adds the 6-byte model identifier and NPort control ports 966–969/4900 (Habr). Lantronix's discovery on UDP/30718 uses a 00 00 00 F8 probe and a 0xF9 setup record (lantronix_telnet_password.rb). Both are 30-line mock responders for CI. Moxa carries many CISA advisories (ICSA-20-056-04 has four CVSS 9.8 CVEs on EDS-G516E/510E (CISA)), but its .ini/CLI export schema is undocumented, so parse is blocked. Caution: the same ports leak credentials (CVE-2016-9361) and FortiGuard has an IDS signature for "Moxa UDP Device Discovery", so PEAT's probe must stay read-only and be documented.

Siemens SCALANCE and RUGGEDCOM ROS (rank 24) fit PEAT's SNMP/HTTPS/Telnet/SSH stack perfectly and have documented text exports — SCALANCE's Load&Save RunningCLI is "a text file of the current configuration as CLI commands" with passwords masked and LogFile is plain ASCII, while Config/ConfigPack/Firmware are binary or "signed and encrypted" (S615 WBM manual); RUGGEDCOM ROS stores "the complete configuration database, in the form of a comma-delimited ASCII text file" config.csv with documented partial-update examples and a Modbus Product Identification register at 0x0000 (Siemens ROS v4.1 guide) — but no public sample of either export exists and no emulator exists, so both are fixture-blocked until an operator donates a file or a recorded SNMP walk.

Software targets: Kepware, Ignition, TwinCAT, VTScada and Niagara

Kepware Server (rank 17) is the best parse-only software target. PTC's 6.0 release notes added "exporting project files to a human-editable JSON format, which replaces the XML format previously used" (PTC What's New 6.0); the demo "will run for 2 hours at a time" with unlimited channels, devices and tags (PTC demo); and the JSON structure (servermain.PROJECT_TITLE, channels[], devices[] with servermain.DEVICE_ID_STRING and driver keys such as modbus_ethernet.DEVICE_ETHERNET_PORT_NUMBER, tags[] with servermain.TAG_ADDRESS) is documented by third parties, as is the Configuration API on HTTP 57412/HTTPS 57512 whose GET /config/v1/project?content=serialize returns the same JSON (Cybus migration guide). The parser therefore doubles as a future pull module and yields a device inventory of everything the OPC server polls. ICSA-24-228-11 names "PTC Kepware Server V6, KEPServerEX V6, Software Toolbox TOP Server V6, and GE IGS V7.6x" as one codebase (CISA), and earlier advisories reached CVSS 9.8 (ICSA-22-242-10, ICSA-20-352-02 (CISA; CISA)), so one parser also covers GE iFIX's bundled Industrial Gateway Server. Caveat: "Project File Encryption" is on by default and must be disabled before JSON export. Scan is Windows-only and form-gated. Effort: parse small-medium.

Ignition (rank 8) has an official Docker image (inductiveautomation/ignition, >1M pulls, ACCEPT_IGNITION_EULA=Y, port 8088) (Docker Hub); unlicensed modules "run for two hours at a time" and "you can reset the timer as many times as you want" (Ignition licensing). The .gwbk backup is a ZIP ("Rename it as .zip. Then extract") containing db_backup_sqlite.idb and project folders (IA forum), parseable with zipfile, sqlite3 and json. Maker Edition is "for non-commercial, personal educational use only" (Maker docs) — do not use it for PEAT fixtures; use trial mode. CISA advisory history and OT prevalence were not researched (gap). Effort: parse medium, scan small.

Beckhoff TwinCAT 3 (rank 18) is the best fixture story and the worst scan story. .TcPOU files hold PLC code as XML with Declaration and Implementation sections, .plcproj is MSBuild XML and .tsproj is TcSmProject XML (ST-LSP TwinCAT); Beckhoff's GitHub organisation (58 repositories) publishes sample projects such as TF6100_Samples "as-is under the Zero-Clause BSD license" (TF6100_Samples; Beckhoff org), though many repos are labelled "Other" and need per-repo checks. ADS is fully documented — Command 0x0001 "ADS Read Device Info" returns version and a 16-byte device name; TCP 48898, UDP 48899 broadcast search, TCP 8016 Secure ADS (TE1000 ADS INTRO) — and pyads is MIT (pyads), so scan code can be written from the spec, but the runtime is a 7-day renewable Windows trial (Beckhoff licensing) and the containerized XAR "is designed for Beckhoff Industrial PCs running Beckhoff Real-Time Linux". Do TwinCAT as a parse module; keep the ADS probe untested until hardware appears.

VTScada / VTScadaLIGHT (rank 25) is free up to 50 I/O tags with "nearly all features enabled" (VTScadaLIGHT) and stores applications as text: AppRoot.SRC, Settings.Dynamic/Settings.Startup (INI-style), Servers.XML, Pages/*.SRC (Files and Folders). CISA's ICSA-22-300-04 (CVSS 7.5, VTScada ≤12.0.38 accepting HTTP(S)) lists energy and water/wastewater as exposed sectors (CISA). Parse is feasible from self-authored fixtures (VTScada script syntax is the effort); scan is Windows-only.

Tridium Niagara (rank 22) is the highest-value building-automation target and the most frustrating. The Fox handshake is fully specified in nmap's fox-info.nse: probe fox a 1 -1 fox hello\n{\nfox.version=s:1.0\nid=i:1\n};; on 1911/4911, reply fox a 0 {...} with hostName, app.name, app.version, vm.version, os.name, hostId, brandId (fox-info.nse), so a PEAT fingerprinter and a mock responder are both small. Parse is blocked: a .dist backup "contains the entire station folder" plus config.bog, licences and certificates (Schneider community), but no free Workbench exists, no sample .dist/.bog was found, and a "Niagara 4.15 Station Bog File Encryption Changes" article could not be opened. Relevance is high — Nozomi's 2025 research produced ten CVEs (CVE-2025-3936 to -3945) with an exploit chain to root and station TLS key theft on misconfigured systems (Nozomi; runZero).

Standards-based primitives multiply vendor coverage

Modbus FC43 Read Device Identification (rank 14) is the cheapest scan upgrade in this report. PEAT's M340 module already issues FC43 (peat/modules/schneider/m340/m340.py, "Method #1: Use Modbus/TCP Function Code 43"), but PEAT has no shared Modbus protocol module — Modbus exists ad hoc in the Woodward, Camlin and M340 code — so promoting FC43 to a generic IPMethod is both a refactor and a coverage win. The pymodbus 3.x simulator (BSD-3, pure Python, Python ≥3.10, 3.16.1 released Oct 2026) takes a JSON config whose server entries include an identity block with VendorName, ProductCode, VendorUrl, ProductName, ModelName, MajorMinorRevision and supports tcp/udp/serial/tls (PyPI pymodbus; simulator config) — a cross-platform CI fixture that can impersonate any Schneider, AutomationDirect, Eaton or Weintek identity. Caveat: "not all Modbus devices support this function", and which Schneider families return which objects was not enumerated. Effort: small.

BACnet/IP (rank 15) gives one module for every building-automation vendor because Device-object identity properties are standardized. Three free simulators exist: bacnet-stack's root Dockerfile runs bacserv on 47808/udp with device instance 1234 and name test_server (core licence GPL-2.0-or-later with GCC linking exception; embedded in shipping Johnson Controls EasyIO controllers) (Dockerfile; bacnet-stack); bacpypes3 (MIT, 0.0.110 released Sept 2026) ships mini-device-revisited.py, custom-server.py and discovery samples in pure Python (samples; PyPI); YABE (MIT) includes three demo servers on Windows/Mono (SourceForge). Who-Is is UDP broadcast, so Docker tests need unicast Who-Is or host networking. There is no vendor-neutral BACnet file to parse. Effort: small-medium.

OPC UA (rank 16) is embedded in CODESYS, TwinCAT, Ignition, FUXA and most modern PLCs, and the standard's FindServers "does not require message security" and returns applicationUri, applicationName and discoveryUrls, while BuildInfo exposes manufacturerName, productName, softwareVersion (OPC UA Part 4; Part 5). Microsoft's OPC PLC is an MIT Docker image on port 50000 with "Anonymous and X.509 certificate authentication ... on by default" (iot-edge-opc-plc); asyncua (LGPL-3.0, 2.1.0 Oct 2026) provides a pure-Python server and uadiscover for non-Docker runners (PyPI asyncua). Effort: medium (new dependency; GetEndpoints plus ServerStatus and namespace reads).

DNP3 Group 0 device attributes (rank 19) are the best multi-vendor substation scan path PEAT lacks. Wireshark's dissector enumerates the variations: 242 software version, 243 hardware version, 245 location, 247 device name, 248 serial number, 250 product name and model, 252 manufacturer, 254 "non-specific all-attributes request", 255 list of variations, 209 Secure Authentication version (packet-dnp.c); DNP.org calls DNP3 "an open and public protocol" widely used in water, transportation and oil and gas (DNP.org). CI oracles are Linux-only: opendnp3 3.1.1 (Apache-2.0, archived 2022 with an end-of-life notice (opendnp3)) has outstation examples, and Sandia's bennu vendors the same opendnp3 inside a GPLv3 Docker build (bennu dnp3 CMakeLists). Python options are weak — dnp3-python ships manylinux wheels only for CPython 3.8–3.10 (PyPI) and pydnp3 must be built from source — so PEAT would write a minimal pure-Python link/transport/application encoder (~1–2k lines, medium effort) and a stub outstation for Windows/macOS runners. Whether opendnp3's example outstation populates Group 0 by default was not verified.

COMTRADE (rank 20) is a near-free parse module that attaches event records to the existing SEL and GE relay modules and the new 61850 module: comtrade (dparrini/python-comtrade) is MIT, supports IEEE C37.111-1991/1999/2013 and IEC 60255-24, reads CFG+DAT and CFF, requires Python ≥3.11, and released 0.2.0 on 2026-10-21 (README; PyPI); its `tests/sample_files` holds 14 fixtures across ASCII, binary, float32 and two encodings (sample_files). libiec61850's MMS file services are "needed for COMTRADE downloads" (libiec61850), so pull comes with the 61850 module.

Two further standards were evaluated and deprioritized: IEC 60870-5-104 has in-process servers (c104 GPLv3 with Linux/Windows wheels (PyPI c104); lib60870; Conpot) but carries no nameplate, so a scan yields only liveness and ASDU address, and US relevance is lower; IEEE C37.118 has pyPMU's TinyPMU TCP simulator (BSD-3) and openPDC (MIT), but pyPMU's only release is a 2017 alpha (iicsys/pypmu; openPDC). SunSpec Modbus is mission-aligned — Sandia co-founded the SunSpec/Sandia DER Cybersecurity Work Group in 2017 (SunSpec) — with Apache-2.0 pysunspec2 and JSON model definitions (pysunspec2; models), but no official simulator exists; PEAT would load the model JSON into the pymodbus simulator's register map (medium effort). Redfish/IPMI are trivially testable (DMTF emulator BSD-3 on port 5000; vaporio/ipmi-simulator GPL-3 on UDP 623 (Redfish emulator; ipmi-simulator)) but are generic IT.

Licensing traps: oracles you cannot use, libraries you cannot link

The most dangerous trap is Step Function I/O's dnp3 library. It is "publicly available under a non-commercial / non-production license, but it is not 'open source'" (stepfunc/dnp3), and Section 2.6 of its licence prohibits using the software "to design, develop, specify, test, validate, or improve any 'Other Implementation'" of the protocol, "including executing it as a test oracle or source of expected results" (LICENSE.txt). It must not appear anywhere in PEAT's DNP3 CI; opendnp3 (Apache-2.0) and bennu (GPLv3) are the safe oracles.

GPLv2-only client libraries cannot be combined with GPLv3 PEAT. The most active Omron libraries — fins 1.0.5 and aphyt 0.1.30 — carry GPLv2 classifiers (PyPI fins); the MIT `finscommand` avoids the problem (PyPI finscommand). Gurux's DLMS libraries are GPL-2.0 dual-licensed (Gurux.DLMS.Python). Conpot is GPL-2.0 (mushorg/conpot) and must stay an external test container, never imported. py61850 is AGPL-3.0 and Python 3.13-only; avoid. Everything else recommended above is MIT, BSD, Apache-2.0, LGPL or GPLv3: python-snap7, s7commplus, pcom, pyclickplc, bacpypes3, comtrade, iec61850 (MIT/Apache), pymodbus (BSD-3), ntc-templates/textfsm/pysunspec2/PyEZ (Apache-2.0), asyncua (LGPL-3), cpppo/ciscoconfparse2/pyiec61850-ng/libiec61850/c104 (GPLv3). The bacpypes3 PyPI metadata disagrees with itself (MIT expression, BSD classifier) — trivial, both permissive.

Reverse-engineered key material is a separate question from licence text. s7commplus bundles legacy S7comm-plus session keys derived from HarpoS7 (MIT), and Rogue7 documents that this mechanism was reverse-engineered from TIA and firmware (Rogue7); Sandia counsel should review before PEAT ships pull over S7comm-plus. The same logic applies to acd-tools (Apache-2.0, alpha, Kaitai-generated parsers for Studio 5000's proprietary .ACD databases (hutcheb/acd)) given Rockwell's EULA clause "You may not reverse assemble, reverse engineer, decompile, translate or create derivative works" (Rockwell EULA copy), to any decryptor for Schneider's .smbp (Claroty showed weak 4-byte XOR and small-keyspace Diffie-Hellman on M221 (Claroty)), and to capture-driven reverse engineering of MicroLogix ladder upload or Do-more's native protocol.

Vendor sample files are copyrighted; PEAT-authored fixtures are not. Rockwell's Sample Code Library prompts a per-download licence agreement whose text could not be retrieved (The Automation Blog); Schneider's demo .xef files are Schneider-copyrighted; Horner's water-treatment .csp demo is a marketing asset; KIT's SCDs are CC BY-NC; Cisco CML images are licensed to CML only; Juniper vJunos is "limited to lab use" under its EULA; Ignition Maker is non-commercial-only; NovaTech NCD "may be installed only on computers owned by the end user ... and only for an Orion-related project". The redistributable exceptions are the standards-body and open-source corpora already listed (IEC XSDs under CC-EULA with attribution, OpenSCD, libiec61850, python-comtrade, ntc-templates, Batfish, VyOS smoketests, Beckhoff 0BSD repos, pycomm3's L5X). For every other parser, generate fixtures in free software and record provenance; the TIA Portal, PLCSIM Advanced, CCW, VisiLogic, Kepware, VTScadaLIGHT and CODESYS Store EULAs were not read and should be before trial-generated exports are committed.

Probing is not free of operational risk. Moxa UDP/4800 and Lantronix UDP/30718 are the same services that leak credentials (CVE-2016-9361; Lantronix password disclosure rated CVSS 10.0), FortiGuard ships an application-control signature for Moxa discovery, and AA26-231A lists TCP 102 scanning and CPU property enumeration as indicators of compromise. PEAT's scan modules should be read-only by construction and documented so defenders can distinguish them from adversary tooling.

Conclusion

The research reframes the question. PEAT's constraint was assumed to be "which devices can we emulate," but the binding constraint turns out to be "which formats come with files we are allowed to commit." Simulators are now abundant and increasingly pure-Python — python-snap7, s7commplus, pymodbus, bacpypes3, asyncua and pyclickplc all run on every GitHub runner OS without Docker — while legally clean fixtures exist for only a handful of formats, nearly all of them standards-based (SCL, COMTRADE) or network-OS (ntc-templates, VyOS). That asymmetry argues for two structural decisions: build the standards layer first (FC43, 61850 SCL/MMS, BACnet, OPC UA, DNP3 Group 0, COMTRADE), because each primitive makes several vendor modules a configuration change rather than a protocol project; and adopt a fixture policy that prefers PEAT-authored exports from free engineering software, recorded with provenance, over any vendor-published sample.

Two sequencing implications follow. A single Windows session with the free or trial IDEs (TIA Portal, CCW Standard, VisiLogic, CLICK, Control Expert, Kepware, VTScadaLIGHT) would unblock the parse side of six Tier 1 candidates at once and settle most of the open format questions, so it is the highest-leverage next step. And because the same emulators and probes PEAT would ship are already in adversary toolkits — AA26-231A names python-snap7 explicitly, AA23-335A describes PCOM brute-forcing on 20256 — each new scan module should be built read-only and documented as a defender's instrument from the first commit, so that the tool that inventories critical-infrastructure PLCs is distinguishable on the wire from the tools that attack them.
