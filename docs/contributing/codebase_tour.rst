********************
Tour of the codebase
********************
What's where in the repository, the areas of the code that deserve extra care, and the
class hierarchy. Read alongside :doc:`/design/architecture`, which explains how the
pieces fit together.

   ├── Dockerfile            The container image
   ├── CHANGELOG.rst         Generated by Towncrier (plus the hand-maintained Known Issues)
   ├── CONTRIBUTING.rst      The contribution process (included in these docs)

Top-level files
---------------
- ``.dockerignore``: files excluded from the container build context
- ``.editorconfig``: consistent editor settings (indentation, line endings)
- ``.gitattributes``: how Git treats file types and line endings, so Bash scripts always
  have ``LF`` endings even when cloned on Windows, and device files keep theirs
- ``.gitignore``: anything that shouldn't be committed (virtualenvs, outputs, caches)
- ``.pre-commit-config.yaml``: the pre-commit hooks
- ``pyproject.toml``: Python packaging metadata, dependencies, and configuration for
  ``pytest``, ``ruff``, ``mypy``, ``codespell``, ``doc8``, ``vulture``, ``towncrier``,
  ``check-sdist``, and the PDM scripts. This is what ``pip install .`` reads.
- ``pdm.lock``: exact versions and hashes of every dependency

The ``peat`` package
====================
.. code-block:: text

   peat/
   ├── __init__.py          Public interface and Loguru setup. Import order matters!
   ├── __main__.py          CLI entry point (python -m peat / the peat executable)
   ├── cli_args.py          argparse definitions, help text, and the --examples cheat sheets
   ├── cli_main.py          CLI logic: dispatch, targets, export, exit codes
   ├── init.py              initialize_peat(): configuration, directories, logging, modules, Elastic
   ├── settings.py          Configuration and State definitions (the config and state singletons)
   ├── settings_manager.py  SettingsManager: layered sources, type conversion
   ├── consts.py            Constants fixed at start-up; must not import other peat modules
   ├── device.py            DeviceModule base class
   ├── module_manager.py    ModuleManager (module_api): lookup and runtime import of modules
   ├── file_signature.py    FileSignature: identify files by content
   ├── elastic.py           Elasticsearch/OpenSearch client wrapper and document export
   ├── es_mappings.py       Elasticsearch index mappings (the schema)
   ├── log_utils.py         Logging sinks and the Elasticsearch log handler
   ├── exit_handler.py      Ordered exit handlers (connections first, files last)
   ├── config_crypto.py     Encryption of configuration files
   ├── results_crypto.py    Encryption of result archives
   ├── utils.py             File writing, hashing, formatting, dates, and other helpers
   ├── api/                 High-level APIs: scan, pull, parse, push, pillage, heat, crypto,
   │                        config builder, and the identify-method models
   ├── config_builder/      The Textual interactive configuration builder
   ├── data/                Data model: models.py (DeviceData and sub-models), store.py (Datastore),
   │                        default_options.py, data_utils.py, validators.py
   ├── heat/                HEAT extractors (FTP via Zeek, Telnet, UMAS) and the Zeek script
   ├── modules/             Device modules, one package per vendor (see device_modules)
   ├── parsing/             Shared parsers: Linux command output, PLCopen TC6 XML to Structured
   │                        Text (plc_open/, vendored), logic generation, ARM CPU IDs
   └── protocols/           Protocol clients and networking: discovery, addresses, interfaces,
                            FTP, Telnet (forked telnetlib), HTTP, SSH, SNMP (+ MIBs), serial,
                            MySQL, ENIP/CIP, PCCC, data packing, manuf OUI database

Vendored and generated code
---------------------------
Some directories are third-party code or generated files that the linters, type checker,
coverage, and spell checker skip (see ``pyproject.toml``): ``peat/parsing/plc_open/``
(the PLCopen editor's XML and code generation modules, GPL), ``peat/protocols/mibs/`` and
``peat/modules/siemens/mibs/`` (compiled SNMP MIBs), ``peat/protocols/forked_telnetlib.py``
(the standard library's ``telnetlib``, removed in Python 3.13),
``peat/modules/woodward/namedlist.py`` and ``csharp_reader.py``, and the enum and protocol
constant tables. Don't reformat them; update them from their sources.

``distribution/``
=================
- ``build-docker.sh``: builds the container image (multi-stage, cached)
- ``build-linux-package.sh``: the portable Linux executable (PyInstaller then StaticX)
- ``peat.spec``, ``sneakypeat.spec``: PyInstaller specs, including data files, hidden
  imports, and excludes
- ``file_version_info.txt``, ``update_file_version_info.py``: Windows executable metadata
- ``peat_icon.ico``, ``tbird.ico``: icons
- ``linux-install-script.sh``: installs the executable and man page; shipped in the Linux
  release bundle
- ``sneakypeat.py``: the lightweight scanner
- ``opensearch-files/``: the Malcolm dashboard and an analyst quickstart

``scripts/``
============
- ``install_peat.sh``, ``install_peat.ps1``: the one-line installers for users
- ``elastic-testing.sh``, ``docker-compose.yml``: a local Elasticsearch and Kibana for
  development and the Elasticsearch tutorial
- ``build_changelog.sh``: preview the changelog with Towncrier
- ``docs_a11y.py``: accessibility checks of the built documentation
- ``module_vendor_ids.py``, ``gen_rtac_events.py``: small API examples and test helpers

``examples/``
=============
Example configuration files (``peat-config.yaml`` is the annotated reference rendered in
the docs), example summaries, the example device module and its inputs and outputs,
SCEPTRE device configurations, encryption examples, target files, and a VS Code
``launch.json``. Several of these are pulled into the documentation with
``literalinclude``, so changing them changes the docs.

Landmines
=========
Some areas of the code are more sensitive or complex than others. If you're unsure about
a change, talk to the other developers (``git log`` shows who to ask). Anything using
advanced Python features that may not be obvious is noted here.

- ``peat/__init__.py``: special setup for Loguru, including custom logging levels, the
  handler for Elasticsearch, and the log levels of third-party loggers (e.g. Scapy).
  **The order of imports in this file matters.**
- ``peat/settings.py``: **absolutely cannot** import or rely on other ``peat`` modules,
  since practically everything imports it (``state`` and ``config``). There is a heavy
  amount of advanced Python hackery here, partly explained in comments. The only changes
  most developers need to make are adding or changing configuration and state variables
  (see :doc:`/design/configuration_and_state`).
- ``peat/consts.py``: must be mostly static at runtime and **absolutely cannot** import
  other ``peat`` modules. Use it for anything determined once at start-up or that never
  changes: string formats, platform information, the run ID.
- ``peat/device.py``: the :class:`~peat.device.DeviceModule` base class overrides some
  "magic methods" (``__init_subclass__`` to bind per-class loggers) and provides the
  wrapper methods that subclasses must not override.
- ``peat/init.py``: :func:`~peat.init.initialize_peat` is the workaround for supporting
  multiple independent ways of using PEAT (the CLI, as a Python package, and
  historically an HTTP server). Changes here affect every entry point.
- ``peat/data/``: the data models use Pydantic (1.x) to provide a convenient interface for
  device data, and define the structure and schema of all output. **Changes here affect
  every module in PEAT** and the Elasticsearch mappings in ``es_mappings.py`` must be kept
  in sync. Think twice, write tests, ask questions.
- ``peat/api/scan_api.py``: port and protocol handling is subtle (configured ports are
  applied per ``(protocol, port)`` and reverted); a past bug let one module's port leak
  into others.
- Several classes use ``@property`` (`Python docs <https://docs.python.org/3/library/functions.html#property>`__)
  and implement "dunder" methods such as ``__str__`` and ``__repr__``
  (`data model docs <https://docs.python.org/3/reference/datamodel.html>`__).
- Pinned dependencies (``requests``, ``pyserial``, ``paramiko``, ``pydantic``, ``pysnmp``)
  are pinned for reasons documented in ``pyproject.toml``; upgrading them is a project,
  not a bump.
