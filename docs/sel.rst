***
SEL
***

There are many Schweitzer Engineering Laboratories (SEL) devices supported by PEAT, including Real Time Automation Controllers (RTACs), the SEL-3620 security gateway, and many types of protection relays. These are implemented by the PEAT modules :class:`~peat.modules.sel.sel_rtac.SELRTAC`, :class:`~peat.modules.sel.sel_3620.SEL3620`, and :class:`~peat.modules.sel.sel_relay.SELRelay`, respectively.

   `SEL Technical Papers <https://selinc.com/literature/technical-papers/>`__

   `SEL products page <https://selinc.com/products/>`__

   `SEL-351S documentation <https://selinc.com/products/351S/docs/>`__

   :class:`~peat.modules.sel.sel_relay.SELRelay`
      PEAT :class:`~peat.device.DeviceModule` implementation for protection relays and other SEL devices

   :class:`~peat.modules.sel.sel_3620.SEL3620`
      PEAT :class:`~peat.device.DeviceModule` implementation for SEL-3620 security gateways

   :class:`~peat.modules.sel.sel_rtac.SELRTAC`
      PEAT :class:`~peat.device.DeviceModule` implementation for SEL RTACs

Relays
------

Relay communications
^^^^^^^^^^^^^^^^^^^^
There are several methods PEAT can interact with a SEL relay: FTP, Telnet, HTTP/HTTPS, and directly connected via serial (currently, EIA-232/RS-232 is supported for serial communications). Device verification and commands (such as relay restart) can be performed via Telnet or Serial, and pulling/pushing of device configuration via FTP or serial.

File output
^^^^^^^^^^^
While the files generated by PEAT may vary by model and device, they roughly follow the following structure:

- ``<device-address>/``

  - ``formatted-logic.txt`` : The logic sections of the configuration.
  - ``parsed-config.json`` : The parsed configuration in JSON format.
  - ``settings.json``, ``settings-meta.json``, ``logic-equations.json`` : Every setting, information about the settings classes, and the SELOGIC control equations (refer to :ref:`sel-settings-records`).
  - ``device-data-full.json`` : All data pulled from the device, including the parsed configuration, telnet data, IP and MAC address, and other information.
  - ``relay_files/``

    - ``CFG.TXT``
    - ``SET_ALL.TXT``
    - ``SETTINGS/``

      - ``... SET_*.TXT ...``

Settings files
^^^^^^^^^^^^^^
The files recovered and/or generated vary by model and device. They may include the following:

- ``CFG.TXT``: basic device data (firmware, model) and a list of the configuration files on the device. Every *relay* has this.
- ``CFG.XML``: similar to the above, in XML format. Seen on the 700G, 710, and 751.
- ``SET_ALL.TXT``: the complete device configuration. This is essentially all of the individual configuration files merged into a single file. The file structure is roughly equivalent to INI with some eccentricities. Most relays have this.
- ``SETTINGS/``: directory containing the individual configuration files (``SET_1.TXT``, etc.). Each file begins with an identical ``[INFO]`` section with the device RELAYTYPE, FID, BFID, and part number, followed by the section for that file (e.g. ``[1]`` in ``SET_1.TXT``). Some relays don't have ``SET_ALL.TXT``. In that case, PEAT reconstructs it from ``CFG.TXT`` and the individual files. When pulling from a relay, the reconstructed file is saved as ``combined_SET_ALL.txt``.

The SEL configuration is stored in a single file called SET_ALL.TXT. This file is broken up into multiple sub files representing sections of the configuration, e.g. ``SET_1.TXT`` for the section ``[SET_1]`` in the full configuration. PEAT pulls this file and the individual files from a device via FTP and parses it into useful information. To change the device configuration, the individual files are uploaded via FTP, then the relay is restarted via a command sent over Telnet. The individual files must be sent due to ``SET_ALL.TXT`` being read-only.

Refer to section 10.26 Virtual File Interface in the SEL-351S Protection System Instruction Manual for detailed descriptions of files present on the relay.

Configuration details
^^^^^^^^^^^^^^^^^^^^^
- RID: Relay Identifier. The Relay Identifier is typically used to identify the relay or the type of protection scheme. The relay tags each report (event report, meter report, etc.) with the Relay Identifier and Terminal Identifier. RID and TID settings may include the following characters: ``0-9, A-Z, -, /, ., space``. These two settings cannot be made via the front-panel interface. (source: SEL-351S Protection System Instruction Manual). The factory default RID for most relays is ``FEEDER 1``.
- TID: Terminal Identifier. Typical Terminal Identifiers include an abbreviation of the substation name and line terminal. The factory default TID for most relays is ``STATION A``.
- SID: Station ID
- FID: Firmware ID (refer to the :ref:`sel-firmware-ids` section below)
- BFID: Boot firmware ID (refer to the :ref:`sel-firmware-ids` section below)
- CT: Current Transformer
- PT: Potential Transformer

.. _sel-firmware-ids:

Firmware IDs
^^^^^^^^^^^^
- FID: Firmware ID
- BFID: Boot firmware ID
   - Similar to FID, but for the boot firmware

- Example FID: ``SEL-351-5-R510-V0-Z103103-D20110429``
   - Model: ``SEL-351``
   - Variant (??) : ``5`` (some devices may not have this portion)
   - Release: ``R510`` (major release, generally new or changed features)
   - Point release: ``V0`` (minor release, usually fixes or minor changes)
   - Settings version: ``Z103103`` (indicates what version of SEL ACSELERATOR software to use)
   - Firmware release date: ``D20110429``

Per SEL's documentation: "The firmware version will be either a standard release or a point release. A standard release adds new functionality to the firmware beyond the specifications of the existing version. A point release is reserved for modifying firmware functionality to conform to the specifications of the existing version."

Setting categories (configuration sections)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
- SET *(X)*: Group settings (where X := [1, 2, 3, 4])
- SEL L(X): Logic settings (where X := [1, 2, 3, 4])
- SET G: Global settings
- SET P(X): Port settings (where X := [1, 2, 3, 4, 5, F]). "F" is the front port, usually RS-232 serial. The port numberings vary by device.
- SET F: Front-Panel settings
- SET R: Report settings
- SET M: Modbus settings
- SET D: DNP3 settings

Settings file format
^^^^^^^^^^^^^^^^^^^^
Settings files are a mix of INI and CSV. Sections are INI-style headers (``[P5]``). The ``[INFO]`` section has ``KEY=VALUE`` lines. Other sections have CSV lines, where the first value is the setting name and the second is the value. The number of columns and the quoting vary by model and firmware:

.. code-block:: text

   [INFO]
   RELAYTYPE=0351S
   FID=SEL-351S-7-R516-V2-Z106105-D20190111
   [CLASSES]
   1,"Group 1","\SETTINGS\SET_1.TXT","a9dd3ac2"
   [1]
   RID,"FEEDER 7","","","","Relay Identifier (30 characters)"
   [L1]
   OUT101,"TRIP"
   [P5]
   "TPORT",23,"23,1025-65534",I,"","Telnet Port (23,1025-65534)"

- 3xx and 7xx relays generally use ``NAME,"VALUE"``, sometimes with four more columns ending in a description.
- 4xx relays generally quote the setting name and add the range and type (``"NAME",VALUE,"RANGE",TYPE,"","Description"``). The 451 truncates setting names longer than 7 characters.
- ``[CLASSES]`` lists the settings classes in the file, with the file they're from and a checksum.
- ``[STORAGE]`` (4xx) lists other files on the relay, such as ``\SWCFG.ZIP``.
- ``[DNPA]`` and ``[DNPB]`` (311L, 387) are DNP3 maps with all of the points in a single space-separated value.
- QuickSet ends each line in the settings in a RDB file with a file separator character (``0x1C``), and some files end with a substitution character (``0x1A``). PEAT removes these before parsing.

Parsing relay files
^^^^^^^^^^^^^^^^^^^
``peat parse -d selrelay`` accepts the following:

- ``SET_ALL.TXT``
- Individual settings files (``SET_1.TXT``, ``SET_P5.TXT``, etc.). A single file only has part of the settings, e.g. ``SET_P5.TXT`` has the network settings but not the logic.
- A directory of relay files, such as the ``relay_files`` directory from a PEAT pull, files downloaded from a relay with FTP, or settings files extracted from a RDB file. Sub-directories (e.g. ``SETTINGS/``) are included and filenames are case-insensitive. If there's no ``SET_ALL.TXT``, it's reconstructed from ``CFG.TXT`` and the ``SET_*.TXT`` files. Event files (``SER.TXT``, ``CSER.TXT``, ``HISTORY.TXT``, ``CHISTORY.TXT``) and ``*.CID`` files in the directory are parsed into the same device. A directory can have files from multiple relays, with each relay's files in its own sub-directory, and each relay is parsed into its own device.
- QuickSet database files (``*.rdb``), see below.
- Output of the ``SHOW`` (``SHO``) command, saved from a Telnet or serial terminal or the QuickSet terminal. See below.
- ``CFG.TXT``, ``SER.TXT``, ``CSER.TXT``, ``HISTORY.TXT``, ``CHISTORY.TXT``, and ``*.CID`` files.

.. code-block:: bash

   peat parse -d selrelay ./SET_ALL.TXT
   peat parse -d selrelay ./relay_files/
   peat parse -d selrelay ./substation.rdb
   peat parse -d selrelay ./sho_output.txt

Example files, and where they're from, are in ``tests/modules/sel/data_files/relay/``.

SHOW command output
^^^^^^^^^^^^^^^^^^^
The ``SHO`` command displays settings in a terminal. Newer relays use ``:=`` and older relays use ``=``, and there may be multiple settings on a line:

.. code-block:: text

   =>>SHO 1
   Group 1

   RID      := SEL-751
   CTR      := 120                CTRN     := 120
   TR       := 50P1T OR 51P1T OR 51G1T OR 50G1T OR SV01T OR
               REMTRIP

   =>SHO L 1
   SELogic group 1
   TR      =M1P + Z1G + 51PT + 51GT + 50P1*SH0

PEAT determines the settings class from the command (``SHO P 5`` is ``[P5]``, ``SHO L 1`` is ``[L1]``), or from the headings in the output (``Group 1``, ``Port 5``, ``SELogic group 1``, ``Global``) if the command wasn't captured. Indented lines without a setting continue the previous setting's value. The output doesn't include the FID, so the model isn't known unless an ``FID=`` line is included (e.g. from the ``ID`` command).

.. _sel-settings-records:

Settings records and SELOGIC equations
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
Whenever PEAT parses relay settings (from a pull, ``SET_ALL.TXT``, individual settings files, a directory of relay files, each relay in a RDB file, ``CFG.TXT``, or ``SHOW`` command output), it saves these files to the device's output directory:

- ``settings.json``: every setting, as a flat list of records in the same order as the settings. Unlike ``parsed-config.json``, nothing is left out: settings that are in a section more than once are all included (PEAT logs a warning for these, since only the last one is used elsewhere), and so are the range, type, and description columns.
- ``settings-meta.json``: information about the settings that isn't a setting: the relay family (``3xx``, ``4xx`` or ``7xx``), the settings classes from ``[CLASSES]`` (name, file and checksum), the "Saved on" lines from QuickSet, and the files in ``[STORAGE]``. This file is only written if there's something to put in it.
- ``logic-equations.json``: the SELOGIC control equations that are set (not ``NA`` or empty), by section and by variable.

If ``CFG.TXT`` is parsed with the other settings files (e.g. in a pull or a directory), its settings are in the same files, since ``SET_ALL.TXT`` includes them.

The columns of a settings line are saved in these fields. Most 300- and 700-series files only have the first two columns.

.. list-table::
   :header-rows: 1

   * - Column
     - Field
     - 400-series example
     - Notes
   * - 1
     - ``name``
     - ``TPORT``
     -
   * - 2
     - ``value``
     - ``23``
     -
   * - 3
     - ``range``
     - ``23,1025-65534``
     - Allowed values
   * - 4
     - ``type``
     - ``I``
     - ``I``, ``U`` and ``S`` have been seen. What they mean isn't documented.
   * - 5
     - ``col5``
     - (empty)
     - Usually empty
   * - 6
     - ``description``
     - ``Telnet Port (23,1025-65534)``
     - Leading and trailing spaces are removed. ``description_raw`` has the column as-is, since some files indent items under a heading (``"      Phase"``).

Fields for columns that aren't in a line are ``null``. Each record also has the ``section`` (settings class, e.g. ``P1``), ``class_name`` and ``file`` (from ``[CLASSES]``, if they're there), ``line_number`` (the line in the settings text that PEAT parsed: ``raw-setall-config.txt`` for settings files, ``CFG.TXT`` itself when it's parsed alone, or ``null`` for ``SHOW`` output), and ``kind``:

.. code-block:: json

   {
       "section": "P5",
       "class_name": "Port 5",
       "file": "/SETTINGS/SET_P5.TXT",
       "line_number": 10,
       "name": "TPORT",
       "value": "23",
       "range": "23,1025-65534",
       "type": "I",
       "col5": "",
       "description": "Telnet Port (23,1025-65534)",
       "description_raw": "Telnet Port (23,1025-65534)",
       "kind": "setting"
   }

In the parsed settings (:func:`~peat.modules.sel.relay_parse.parse_config_data`) each setting still has a ``value`` and a ``description``, and ``range``, ``type`` and ``col5`` are added if they aren't empty. The description is only taken from the sixth column. Before, the last column was used, so a line like ``"URETRY1",3,2~10`` had a description of ``2~10``.

SELOGIC control equations and the settings they use (timers, counter presets, etc.) are in the same settings classes, and many equations have values like ``0``, ``1``, ``NA`` or a single Relay Word bit. The ``kind`` of each setting is one of:

- ``equation``: a SELOGIC control equation, e.g. ``TR`` (trip), ``ULCL`` (unlatch close), ``SV01``, ``OUT101``, ``87M2TC`` (torque control), or ``T01_LED``
- ``equation_unset``: an equation that isn't used (``NA`` on 700-series relays, or empty), or a free-form logic line that's blank or only has a comment
- ``setting``: anything else, e.g. ``TDURD`` (minimum trip duration), ``CFD``/``CFDX`` (close failure time delay), ``SV01PU`` (timer pickup), ``OUT101FS`` (output fail-safe), or text such as ``RID`` and ``TID`` (identifiers), ``DP01`` (display points) and ``NLB01`` (local bit labels)
- ``bit_list``: a list of Relay Word bits for the Sequential Events Recorder, e.g. ``SER1``
- ``alias``: a Relay Word bit alias (700-series), e.g. ``ALIAS4`` set to ``JAMTRIP LOAD_JAM_TRIP PICKUP DROPOUT``

PEAT classifies settings by name first (known equation names, then the timer and enable settings that go with them), and then by the syntax of the value. The relay family, from the ``RELAYTYPE`` or ``FID``, determines the SELOGIC dialect:

- 300-series (e.g. SEL-311C, SEL-351S): symbols (``*`` AND, ``+`` OR, ``!`` NOT, ``/`` and ``\`` rising and falling edge), e.g. ``TR = M1P + Z1G + 50P1*SH0``. Every setting in the logic classes (``L1``-``L6``) is an equation.
- 700-series (e.g. SEL-710, SEL-751) and 400-series (e.g. SEL-421, SEL-487E): keywords (``AND``, ``OR``, ``NOT``, ``R_TRIG``, ``F_TRIG``), comparisons and math functions, e.g. ``TR := 50P1T OR (27P1T AND NOT LOP)``. A value only counts as an equation if its operators and operands alternate, so text like ``FEEDER A OR B`` is a setting. Outside the logic classes (``L`` and ``A``), a setting that isn't a known equation also needs an operator between two operands (``AND``, ``OR`` or a comparison) and uppercase Relay Word bits, so labels like ``NOT USED`` or ``Feeder OR Bus`` are settings.
- 400-series protection (``L``) and automation (``A``) logic is free-form: each line (``PROTSELn`` or ``AUTO_n``) is split into the variable, the equation and the comment, which are saved in the record's ``lhs``, ``rhs`` and ``comment`` fields. For example, ``PSV01 := R_TRIG 52AA1 # Pulse for each close``. Lines that set a timer's pickup, dropout or preset time, or a counter's preset, to a number (``PCT01PU := 5.3``, ``PCN01PV := 500``) are settings, since these are the timers and presets of the logic. If they're set to a math expression, they're equations.

``logic-equations.json`` groups the equations by section and by the variable they belong to. Each variable has the ``value`` of its own equation, and the ``parts`` that go with it in the same section, such as the timers for a SELOGIC variable or the set and reset equations for a latch. Comments from free-form logic are in ``comments``. If free-form logic assigns the same variable more than once, ``value``, ``parts`` and ``comments`` have the last assignment, and ``assignments`` has all of them in order (``name``, ``value`` and ``comment``):

.. code-block:: json

   {
       "1": {
           "TR": {"value": "49T OR LOSSTRIP OR JAMTRIP", "parts": {}}
       },
       "L1": {
           "SV01": {"value": "WDGTRIP OR BRGTRIP", "parts": {"SV01PU": "0.00", "SV01DO": "0.00"}},
           "LT01": {"value": null, "parts": {"SET01": "IN101", "RST01": "IN102"}},
           "OUT103": {"value": "TRIP OR PB04", "parts": {"OUT103FS": "Y"}}
       }
   }

The equations are also in these places:

- ``parsed-config.json`` has ``logic_equations`` (every equation that's set, by section and name) and ``logic_settings`` (the settings used by the logic that aren't equations, such as ``TDURD``, ``SV01PU`` and the 400-series ``PCN01PV := 500``). The existing ``close_logic``, ``output_logic`` and ``trip_logic`` don't change: they only include some of the equations, and they include some timers (e.g. ``TDURD`` and ``CFD``).
- ``logic.formats["selogic-equations"]`` in the device data is a text listing of the equations that are set, e.g. ``TR := 50P1T OR 51P1T``. This is included in the Elasticsearch data. The settings records aren't, since there are thousands of them.

.. _sel-setting-annotations:

Setting annotations
^^^^^^^^^^^^^^^^^^^
Many settings files only have the name and value of each setting (``NETMODE,"FAILOVER"``), and the names are short mnemonics. PEAT adds these fields to each record in ``settings.json`` (refer to :ref:`sel-settings-records`):

- ``full_name``: a short name, e.g. ``Ethernet operating mode``
- ``description``: what the setting does. This is the sixth column of the settings file if it has one, otherwise PEAT's description.
- ``description_source``: where the description is from: ``device`` (the settings file), ``user`` (your descriptions file, see below), ``peat`` (PEAT's table of settings), ``pattern`` (PEAT's patterns for numbered and protection element settings), or ``null`` if there isn't one
- ``allowed_values``: the values or ranges the setting can have, e.g. ``["FIXED", "FAILOVER", "SWITCHED"]`` or ``["23", "1025-65534"]``, and ``allowed_values_source`` (the same sources as the description)
- ``units``: e.g. ``min``, ``s``, ``cycles``, ``ms``
- ``security``: ``true`` if the setting enables a network service or limits access, e.g. ``ETELNET``, ``EFTPSERV``, ``FTPANMS``, ``MAXACC``, ``FASTOP``, ``T_OUT`` and ``DSABLSET``

``class_name`` is filled in from PEAT's names for the settings classes if the settings don't have a ``[CLASSES]`` section. The meaning of some class letters depends on the relay family: ``M`` is the Modbus map on 300- and 700-series relays and the breaker monitor on 400-series relays, and ``T`` is text labels on 300-series relays and aliases on 400-series relays.

.. code-block:: json

   {
       "section": "P1",
       "name": "NETMODE",
       "value": "FAILOVER",
       "full_name": "Ethernet operating mode",
       "description": "How the two Ethernet ports are used. FIXED only uses the port in NETPORT, ...",
       "description_source": "peat",
       "allowed_values": ["FIXED", "FAILOVER", "SWITCHED"],
       "allowed_values_source": "peat",
       "units": null,
       "security": false
   }

Each field is taken from the first of these that has it:

#. The device: the description and range columns of the settings file. Most 400-series files have these (``"TPORT",23,"23,1025-65534",I,"","Telnet Port (23,1025-65534)"``). A description from the device is never replaced. The full name is the description without the values in parentheses at the end, unless it's indented (an item under a heading). The allowed values are from the range column, or the values in parentheses at the end of the description (``Transport Protocol (UDP,TCP)``). The 400-series range ``2~10`` is ``2-10``.
#. Your descriptions file, from the ``sel.setting_descriptions_file`` option (see below).
#. PEAT's table of about 200 common and security-relevant settings (``SETTING_INFO`` in :mod:`peat.modules.sel.sel_setting_info`). Values for a model (e.g. the SEL-351S) take precedence over values for a family (``3xx``, ``4xx``, ``7xx``), since the same setting can have different values: ``NETMODE`` is ``FIXED, FAILOVER, SWITCHED`` on 700-series relays and the SEL-351S adds ``PRP``, and ``MAXACC`` is ``0, 1, B, 2, C`` on the SEL-351S and ``1, B, P, A, O, 2, C`` on 400-series relays. Some settings have different names by family (``T_OUT`` and ``TIMEOUT``, ``BITS`` and ``DATABIT``, ``EFTPSERV`` and ``FTPSERV``), and port settings are only matched in the port classes.
#. Patterns for numbered settings (``SV05``, ``SET01``, ``OUT403``, ``IN101D``, ``DNPIP2``, ``T01_LED``, ``PB3B_LED``, ``SER1``, ``MOD_001``, and the 400-series ``PSV``, ``PMV``, ``PLT``, ``PCT``, ``PST``, ``PCN``, ``ASV``, ``AMV``, ``ALT``, ``AST`` and ``ACN01`` (counter) variables), the X-side and Y-side settings of the SEL-700G (``TRX``, ``CFDX``), protection element settings, element enables, and torque control equations. Element settings are named from the element and what the setting is: ``50P1P`` is "Phase instantaneous overcurrent level 1 pickup", ``51AC`` is the curve of the phase A time-overcurrent element, and ``87M2TC`` is the torque control equation of motor differential level 2. ``P`` is the pickup, ``D`` a time delay, ``TP`` the trip pickup, ``TC`` the torque control, and for inverse-time (51) elements ``C`` is the curve, ``TD`` the time dial, ``RS`` electromechanical reset, ``CT`` the constant time adder and ``MR`` the minimum response time. Elements that PEAT doesn't know aren't described, rather than guessed.

For 400-series free-form logic, the line (``PROTSEL1``) is described by the variable it assigns (``PSV01``).

The SELOGIC control equations in ``logic-equations.json`` also have a ``full_name`` and ``description`` (if they're known), and ``part_names`` with the full names of their parts (e.g. ``SV01PU`` is "SV01 timer pickup time"). ``formatted-logic.txt`` has the same logic as before, followed by a listing of the equations with their full name and description as a comment under each. This listing is only in the file: ``logic.parsed`` in the device data doesn't change.

A small, flat summary of the security-relevant settings is saved to ``extra.sel_security_settings`` in the device data. It has the value of each setting flagged as ``security``, keyed by ``<section>.<name>`` (e.g. ``"P1.ETELNET": "Y"``), and:

- ``enabled_services``: network services enabled on ports that aren't turned off, from ``telnet``, ``ftp``, ``http``, ``iec61850``, ``goose``, ``mms_file_services``, ``dnp3`` and ``modbus``
- ``anonymous_ftp``: if anonymous FTP logins are allowed (only if the relay has the ``FTPANMS`` setting)
- ``fast_operate_ports``: ports that accept SEL Fast Operate messages
- ``disabled_ports``: ports that are turned off (``EPORT := N``)

The services in the summary are from the settings. They don't say if a port is connected, or if the relay has the hardware option for a protocol.

**Your own descriptions.** Set ``sel.setting_descriptions_file`` (in the YAML config file) to the path of a JSON file with the same format as ``SETTING_INFO``: an object keyed by setting name, where each entry can have ``name``, ``desc``, ``values`` (a string such as ``"Y, N"`` or a list), ``units``, ``security``, ``sections`` (a regular expression for the classes the entry applies to), ``only`` (a list of families), ``by_family`` and ``by_model`` (objects with the same keys, for a family or model). Your entries take precedence over PEAT's, but not over the device's own descriptions. Unknown keys and values of the wrong type (e.g. ``"security": "no"`` instead of ``false``, or a number for ``values``) are ignored with a warning, so a mistake only affects that key. You can, for example, write descriptions for the settings of your relays from their instruction manuals. Since SEL's manuals are copyrighted, don't share or commit a file with text copied from them.

.. code-block:: json

   {
       "NETMODE": {
           "name": "Ethernet operating mode",
           "desc": "How the Ethernet ports are used",
           "values": "FIXED, FAILOVER, SWITCHED, PRP",
           "by_model": {"710": {"values": "FIXED, FAILOVER, SWITCHED"}}
       }
   }

**Sources.** PEAT's descriptions are written by PEAT's authors. Setting names, allowed values, ranges and units are facts from the settings sheets and settings tables of the public SEL-351S (date code 20171023), SEL-421 (20130627), SEL-487B (20090519), SEL-700G (20150521), SEL-710 (20090327), SEL-751A (20130329) and SEL-787 (20150130) instruction manuals. Values change between firmware versions, which is why the values from the device's own range column are used first. No openly licensed dictionary of SEL settings exists, and PEAT doesn't include text from SEL's manuals.

.. _sel-protection-schemes:

Protection schemes and device function numbers
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
``parsed-config.json`` has ``protection_schemes``, the protection elements that are enabled in any settings group, keyed by device function code (e.g. ``{"50P": "Phase instantaneous overcurrent"}``), and ``protection_schemes_by_group``, the same for each settings group (``{"1": {"50P": "..."}}``). An element is enabled by a setting named ``E`` and the code, e.g. ``E50P``, ``E87M`` or ``E49MOTOR``. The code has two digits, so ``E61850`` (IEC 61850) and ``E2SPEED`` (two-speed motor) aren't elements, and ``E32IV`` is a SELOGIC equation. An enable is off if it's ``N``, ``NO``, ``OFF``, ``NONE``, ``0`` or empty. Anything else enables it, since many enables are a number of levels (``E50P := 3``), shots (``E79 := C2``) or a mode (``E32 := AUTO``, ``E49RTD := INT``, ``E87 := GEN``). On relays with ``EVOLT := Y`` (e.g. the SEL-351S), voltage elements with a pickup that isn't ``OFF`` or zero are also included. On the SEL-487E, the free-form protection logic lines of each section are also in ``protection_schemes``, keyed by the section.

The names are from :func:`~peat.modules.sel.sel_elements.ansi_name`, which uses PEAT's names for SEL elements first, since SEL uses some letters in its own way: ``P`` is phase, ``G`` is residual ground (3I0), ``N`` is neutral (the IN channel), ``Q`` is negative sequence, ``27S`` and ``59S`` are on the synchronism-check voltage channel (VS), ``68`` is out-of-step blocking, ``78`` is out-of-step tripping, ``87N`` is restricted earth fault, ``25BK1`` and ``25BK2`` (SEL-421) are the synchronism checks for breakers 1 and 2, ``81ACC`` (SEL-700G) is the off-frequency time accumulators, and ``X`` and ``Y`` at the end (SEL-700G) are the X-side and Y-side terminals. Codes that aren't known use the names in ``ANSI_CODES`` (in ``sel_consts.py``), then the IEEE C37.2-2008 name of the number, with SEL's meanings of the suffix letters (``BK`` is a breaker, so ``25BK3`` is "Synchronism check (breaker) #3").

The vendor-neutral table of IEEE C37.2-2008 device function numbers (1-99), with the device 16 (data communications device) suffix scheme, common suffix letters and the acronyms, is in :mod:`peat.parsing.ieee_c37_2`. :func:`~peat.parsing.ieee_c37_2.describe_device_function` describes codes such as ``51G``, ``87T2``, ``16ESM`` and ``50/51``. The names are from IEEE Std C37.2-2008, as printed in U.S. Bureau of Reclamation FIST Volume 3-8, "Operation, Maintenance, and Field Test Procedures for Protective Relays and Associated Circuits" (2011), Appendix B, a public domain U.S. government work.

SEL software: RDB Project Files
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
SEL configuration software (ACSELERATOR QuickSet) stores device configurations in project files with a ``.rdb`` file extension. The ``.rdb`` SEL project files use a file structure called Compound File Binary Format, or Microsoft OLE2 File. PEAT uses the ``olefile`` method ``isOleFile()`` to check the file for the magic number at the start of the header to determine if it is the correct format.

A RDB file can have settings for multiple relays, with a storage for each relay:

.. code-block:: text

   Relays/
       <relay name>/
           Misc/
               Cfg.txt       (same as CFG.TXT on a relay)
               Device.txt    (name of the relay in QuickSet)
               Version       (QuickSet version and when the settings were saved)
               GL1.gle, ...  (logic diagrams)
           set_1.txt, set_P1.txt, ...

Filenames may be lowercase (``set_1.txt``) or uppercase (``SET_1.TXT``), and PEAT matches them without regard to case. PEAT combines each relay's ``Cfg.txt`` and settings files into the ``SET_ALL`` format (saved as ``extracted_SET_ALL.txt``), and parses it with the same code used for configurations pulled from devices. The "Saved on" date from ``Version`` is used for the logic's created and last updated times. The name of the relay in the RDB file is saved in ``extra.rdb_relay_name``.

If there are multiple relays in the file, each relay is parsed into its own device and exported to files. Only the first relay is included in the parse results summary. Relays with the same IP address (e.g. defaults in templates) are kept as separate devices, with an ID of ``<rdb file name>_<relay name>``. The other relays are also exported to Elasticsearch, if it's enabled.


Configured IED Description (.CID) Files
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
``.CID`` files are zlib-compressed text data. This may be :term:`XML` data, or it could be other data. The only file we've seen so far is ``SET_61850.CID``, and it decompresses to XML. The schema for the XML is (I think) standardized by IEC 61850-6. If you are willing to pay for a copy of the standard, then maybe you can make some use out of the XML. It's only relevant if IEC61850 or GOOSE is enabled.

If any ``.CID`` files are found during a PEAT pull, PEAT will attempt to decompress them and put the results in the device output directory with the name of ``decompressed_<filename>.xml`` (or ``.txt`` if non-XML data was extracted from the file). They can also be parsed directly with ``peat parse -d selrelay <filename>`` (e.g. ``peat parse -d selrelay ./SET_61850.CID``).

To manually extract them without using PEAT:

.. code-block:: bash

   sudo apt update
   sudo apt install qpdf
   zlib-flate -uncompress < ./SET_61850.CID > SET_61850.xml


Developer notes on SEL communications
-------------------------------------
SEL relays can communicate over Telnet, serial connection (e.g. RS-232), or a "engineering tunnel" through a SEL 3530 RTAC (I'm not aware of any relays that support SSH yet, but there might be some newer ones that do). The messages sent are part of what they call "SEL ASCII" commands, and those commands are transport-agnostic, which means the "id" command sent over Telnet will have the same response as one sent over serial or an engineering tunnel. The commands and responses are basic ASCII text, except in certain cases, where it's "Compressed ASCII" (this is rare).

In addition to "SEL ASCII" interfaces, relays also typically have :term:`FTP` and a web interface (using :term:`HTTP` and/or HTTPS), dependent on the configuration. FTP is typically disabled by default, but can be enabled. Since files can be transferred over "ASCII" or FTP, and the commands are very similar, the file transfer code has been generalized in ``peat/modules/sel/sel_comms.py``.

In PEAT, the "SEL ASCII" commands are implemented as a transport-agnostic class, :class:`~peat.modules.sel.sel_ascii.SELAscii`. The sub-classes for specific transports are :class:`~peat.modules.sel.sel_telnet.SELTelnet` and :class:`~peat.modules.sel.sel_serial.SELSerial`. We don't have support for engineering tunnels through an RTAC (yet). The code for scraping and parsing web pages is implemented by :class:`~peat.modules.sel.sel_http.SELHTTP`. Some of the web pages literally run ASCII interface commands internally and just display the results, while other pages pull data in other ways, so there is some overlap in parsing functionality between :class:`~peat.modules.sel.sel_http.SELHTTP` and :class:`~peat.modules.sel.sel_ascii.SELAscii`. The :term:`FTP` interface isn't terribly special, except for a few quirks. The FTP functionality is implemented in ``peat/modules/sel/sel_comms.py`` with functions that call PEAT's generic :class:`~peat.protocols.ftp.FTP` class and handle a few quirks (like changing directories on older relays).

The code gets called from :class:`~peat.modules.sel.sel_relay.SELRelay` class, in the various ``pull_*`` and ``_verify_*`` methods. The ``pull_*`` methods get called by ``pull_project``, which is the function that gets called by PEAT when ``peat pull`` happens, and is defined in the :class:`~peat.device.Device` base class.

YMODEM notes
^^^^^^^^^^^^

YMODEM is required for relays that don't have the ``file show`` command. PySerial doesn't support YMODEM, and the Python ``modem`` package hasn't been updated in over 11 years, so we're forced to subprocess and call the ``rz`` / ``sz`` commands from the ``lrzsz`` project. This is not available on Windows, but is available on Linux (``sudo apt install lrzsz``) and MacOS (``sudo brew install lrzsz``).

- ``show`` supported: 700G, 351S, 351
- ``read``: 451, 2032 (Requires Ymodem to transfer the file)


Things that don't require YMODEM and use ``fil show``

- 351S doesn't require YMODEM and uses ``fil show``.
- 351S was tested on peat rack (port F, front serial, 9600 baud)
- 351 on peat rack tested (port F, front serial, 57600 baud)
- 700G on peat rack tested (port 3, rear serial, 9600 baud)
- 751 should work with ``fil show`` according to the documentation.
- 710 should also work according to the docs
- 311C-1 has ``file show``, according to docs.

Things that DO require YMODEM for file transfer

- 451: DOES require YMODEM for file transfer. It uses ``fil read <file>`` instead of ``fil show``.
- 451: YMODEM with "file read".
- 487E: YMODEM with "file read".
- 2030 (and 2032?): YMODEM with "file read".

XMODEM devices

- NOTE: XMODEM only works for SELboot, doesn't work during normal operations, according to docs. basically lets you upload and download firmware updates.
- 300G. According to docs it doesn't have any "fil" commands, and also requires XMODEM for transfers.
- 311A. Same as above, according to docs.
- 311L-0-6. Same as above.
- 311L-1-7. Same as above.
- 387. same as above.
- 387A. same as above.
- 587Z. same as above.

Others

- 387L. Not even xmodem...
- 587. not even xmodem.

Telnet notes
^^^^^^^^^^^^

Full list of Telnet commands is in the instruction manual.

From the docs:

   "A command transmitted to the relay consists of the command followed by
   either a CR (carriage return) or a CRLF (carriage return and line feed). You
   can truncate commands to the first three characters. For example, EVENT 1
   <Enter> becomes EVE 1 <Enter>. Use upper- and lowercase characters
   without distinction, except in passwords.

   Each message begins with the start-of-transmission character (ASCII 02) and
   ends with the end-of-transmission character (ASCII 03). Each line of the
   message ends with a carriage return and line feed."
