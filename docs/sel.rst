***
SEL
***

There are many Schweitzer Engineering Laboratories (SEL) devices supported by PEAT, including Real Time Automation Controllers (RTACs), the SEL-3620 security gateway, and many types of protection relays. These are implemented by the PEAT modules :class:`~peat.modules.sel.sel_rtac.SELRTAC`, :class:`~peat.modules.sel.sel_3620.SEL3620`, and :class:`~peat.modules.sel.sel_relay.SELRelay`, respectfully.

   `SEL Technical Papers <https://selinc.com/literature/technical-papers/>`__

   `SEL products page <https://selinc.com/products/>`__

   `SEL-351S documentation <https://selinc.com/products/351S/docs/>`__

   :class:`~peat.modules.sel.sel_relay.SELRelay`
      PEAT :class:`~peat.device.DeviceModule` implementation for protection relays and other SEL devices

   :class:`~peat.modules.sel.sel_3620.SEL3620`
      PEAT :class:`~peat.device.DeviceModule` implementation for SEL-3620 security gateways

   :class:`~peat.modules.sel.sel_rtac.SELRTAC`
      PEAT :class:`~peat.device.DeviceModule` implementation for SEL RTACs

Relays
------

Relay communications
^^^^^^^^^^^^^^^^^^^^
There are several methods PEAT can interact with a SEL relay: FTP, Telnet, HTTP/HTTPS, and directly connected via serial (currently, EIA-232/RS-232 is supported for serial communications). Device verification and commands (such as relay restart) can be performed via Telnet or Serial, and pulling/pushing of device configuration via FTP or serial.

File output
^^^^^^^^^^^
While the files generated by PEAT may vary by model and device, they roughly follow the following structure:

- ``<device-address>/``

  - ``formatted-logic.txt`` : The logic sections of the configuration.
  - ``parsed-config.json`` : The parsed configuration in JSON format.
  - ``device-data-full.json`` : All data pulled from the device, including the parsed configuration, telnet data, IP and MAC address, and other information.
  - ``relay_files/``

    - ``CFG.TXT``
    - ``SET_ALL.TXT``
    - ``SETTINGS/``

      - ``... SET_*.TXT ...``

Settings files
^^^^^^^^^^^^^^
The files recovered and/or generated vary by model and device. They may include the following:

- ``CFG.TXT``: basic device data (firmware, model) and a list of the configuration files on the device. Every *relay* has this.
- ``CFG.XML``: similar to the above, in XML format. Seen on the 700G, 710, and 751.
- ``SET_ALL.TXT``: the complete device configuration. This is essentially all of the individual configuration files merged into a single file. The file structure is roughly equivalent to INI with some eccentricities. Every relay has this.
- ``SETTINGS/``: directory containing the individual configuration files (``SET_1.TXT``, etc.). Each file contains an identical ``[1]`` section at the beginning with the device relaytype, FID, BFID, and part number.

The SEL configuration is stored in a single file called SET_ALL.TXT. This file is broken up into multiple sub files representing sections of the configuration, e.g. ``SET_1.TXT`` for the section ``[SET_1]`` in the full configuration. PEAT pulls this file and the individual files from a device via FTP and parses it into useful information. To change the device configuration, the individual files are uploaded via FTP, then the relay is restarted via a command sent over Telnet. The individual files must be sent due to ``SET_ALL.TXT`` being read-only.

Refer to section 10.26 Virtual File Interface in the SEL-351S Protection System Instruction Manual for detailed descriptions of files present on the relay.

Configuration details
^^^^^^^^^^^^^^^^^^^^^
- RID: Relay Identifier. The Relay Identifier is typically used to identify the relay or the type of protection scheme. The relay tags each report (event report, meter report, etc.) with the Relay Identifier and Terminal Identifier. RID and TID settings may include the following characters: ``0-9, A-Z, -, /, ., space``. These two settings cannot be made via the front-panel interface. (source: SEL-351S Protection System Instruction Manual). The factory default RID for most relays is ``FEEDER 1``.
- TID: Terminal Identifier. Typical Terminal Identifiers include an abbreviation of the substation name and line terminal. The factory default TID for most relays is ``STATION A``.
- SID: Station ID
- FID: Firmware ID (refer to the :ref:`sel-firmware-ids` section below)
- BFID: Boot firmware ID (refer to the :ref:`sel-firmware-ids` section below)
- CT: Current Transformer
- PT: Potential Transformer

.. _sel-firmware-ids:

Firmware IDs
^^^^^^^^^^^^
- FID: Firmware ID
- BFID: Boot firmware ID
   - Similar to FID, but for the boot firmware

- Example FID: ``SEL-351-5-R510-V0-Z103103-D20110429``
   - Model: ``SEL-351``
   - Variant (??) : ``5`` (some devices may not have this portion)
   - Release: ``R510`` (major release, generally new or changed features)
   - Point release: ``V0`` (minor release, usually fixes or minor changes)
   - Settings version: ``Z103103`` (indicates what version of SEL ACSELERATOR software to use)
   - Firmware release date: ``D20110429``

Per SEL's documentation: "The firmware version will be either a standard release or a point release. A standard release adds new functionality to the firmware beyond the specifications of the existing version. A point release is reserved for modifying firmware functionality to conform to the specifications of the existing version."

Setting categories (configuration sections)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
- SET *(X)*: Group settings (where X := [1, 2, 3, 4])
- SEL L(X): Logic settings (where X := [1, 2, 3, 4])
- SET G: Global settings
- SET P(X): Port settings (where X := [1, 2, 3, 4, 5, F]). "F" is the front port, usually RS-232 serial. The port numberings vary by device.
- SET F: Front-Panel settings
- SET R: Report settings
- SET M: Modbus settings
- SET D: DNP3 settings

SEL software: RDB Project Files
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
SEL configuration software stores device configurations in project files with a ``.rdb`` file extension. The ``.rdb`` SEL project files use a file structure called Compound File Binary Format, or Microsoft OLE2 File. PEAT uses the ``olefile`` method ``isOleFile()`` to check the file for the magic number at the start of the header to determine if it is the correct format. If it is, the ``SET_ALL`` configuration for the device is extracted and parsed (with the same parsing code used for configurations pulled form devies).


Configured IED Description (.CID) Files
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
``.CID`` files are zlib-compressed text data. This may be :term:`XML` data, or it could be other data. The only file we've seen so far is ``SET_61850.CID``, and it decompresses to XML. The schema for the XML is (I think) standardized by IEC 61850-6. If you are willing to pay for a copy of the standard, then maybe you can make some use out of the XML. It's only relevant if IEC61850 or GOOSE is enabled.

If any ``.CID`` files are found during a PEAT pull, PEAT will attempt to decompress them and put the results in the device output directory with the name of ``decompressed_<filename>.xml`` (or ``.txt`` if non-XML data was extracted from the file). They can also be parsed directly with ``peat parse -d selrelay <filename>`` (e.g. ``peat parse -d selrelay ./SET_61850.CID``).

To manually extract them without using PEAT:

.. code-block:: bash

   sudo apt update
   sudo apt install qpdf
   zlib-flate -uncompress < ./SET_61850.CID > SET_61850.xml


RTACs
-----

PEAT can pull data from a live RTAC (over HTTP/HTTPS and PostgreSQL), and parse an RTAC project that was exported from ACSELERATOR RTAC (SEL-5033). The first sections are about parsing project exports, and the last sections are about the TLS certificate of the web interface, the hashes of the files PEAT collects, and the engineering access paths in the configuration of the RTAC.

The web pull logs in with the credentials that worked during the scan (one of the ``web.users`` and ``web.passwords`` options), or with the ``web.user`` and ``web.pass`` options. RTACs don't have default credentials, so a pull with ``--skip-scan`` needs the ``web.user`` and ``web.pass`` options, otherwise the web pull is skipped.

.. _sel-rtac-project-exports:

RTAC project exports
^^^^^^^^^^^^^^^^^^^^
PEAT can't parse the project files that ACSELERATOR RTAC saves. To get files that PEAT can parse, export the project from ACSELERATOR RTAC. The export is a directory of XML files, with one XML file for each item in the project tree. A typical export looks like this:

- ``Project Info.xml``: the RTACs in the project (model and export schema version), and the project description.
- ``Navigator Layout.xml``: the layout of the project tree in the editor. PEAT ignores this file.
- ``SEL_RTAC/``: the items of the RTAC (the name of this directory is the ``FolderName`` in ``Project Info.xml``).

  - ``Tag Processor.xml``: the tag mappings.
  - ``System/Main Controller.xml``: the task cycle times, and the programs that each task runs.
  - ``System/Contact I_O.xml``: the physical contact inputs and outputs.
  - ``System/SystemTags.xml``: the RTAC system tags (alarms, diagnostics, LEDs, etc.).
  - ``System/System_Time_Control.xml``: the time source and time zone settings.
  - ``Advanced Read-in Items/``: device settings, such as ``Ethernet Settings.xml`` (IP addresses and MAC addresses) and ``Website Settings.xml`` (host name). These are only in some exports.
  - One XML file for each device connection, GOOSE message, tag list, program (POU), global variable list (GVL), data type, and user library. These can be in any subdirectory, because the user can make folders in the project tree.

- ``POUs/``: the shared user logic of the project (objects that are not inside an RTAC), such as the ``Library Manager``.

PEAT can parse these inputs:

- The export directory: ``peat parse -d selrtac -- ./MyProject/``
- A tarball of the export directory (``.tar``, ``.tar.gz`` or ``.tgz``): ``peat parse -d selrtac -- ./myproject-rtac.tar.gz``. The file name must match one of the patterns in :attr:`~peat.modules.sel.sel_rtac.SELRTAC.filename_patterns` (e.g. it contains ``rtac``) for PEAT to find it without ``-d selrtac``.
- A single XML file from an export: ``peat parse -d selrtac -- "./MyProject/SEL_RTAC/System/Main Controller.xml"``. Without ``-d``, PEAT finds RTAC XML files by their ``<RTACModule>`` root element.

XML file format
^^^^^^^^^^^^^^^
Every file has a ``<RTACModule>`` root element with one child element. The tag of the child is the type of the item. Most items start with an ``<ExportSource>`` element:

.. code-block:: xml

   <RTACModule>
     <Device>
       <ExportSource>
         <Schema>22</Schema>
         <DeviceMOT>3530</DeviceMOT>
       </ExportSource>
       <Name>CB101</Name>
       ...
     </Device>
   </RTACModule>

- ``Schema`` is the version of the export format. It increases with the version of ACSELERATOR RTAC. Public exports have schemas from 18 to 36.
- ``DeviceMOT`` is the model option table of the RTAC. It can be the model (``3530``, ``3555``) or the full part number (e.g. ``3530HB0AX313X1XXXXXX``). PEAT uses the first four digits as the model, and a full part number as the part number. ``Project Info.xml`` has the ``DeviceMOT`` of each RTAC in the project, and PEAT uses it first. If the default host name in ``Website Settings.xml`` has a more specific model (e.g. ``SEL3530-4-0030A702E165``), PEAT uses it.

Some files start with a UTF-8 byte order mark (BOM), and some have an XML declaration. PEAT reads the files with the ``utf-8-sig`` encoding, which removes the BOM.

Settings and tags are in ``<SettingPages>``. Each ``<SettingPage>`` has a ``<Name>`` and ``<Row>`` elements, and each row has ``<Setting>`` elements (cells) with a ``<Column>`` and a ``<Value>``. There are two forms of page:

- A list of single settings, with the columns ``Setting``, ``Value`` and ``Comment``. This is the form of the ``Settings`` page of a device, e.g. ``Server IP Address`` and ``Server IP Port``.
- A table, with one row for each tag, register, poll, or similar. For example the ``Binary Inputs`` page of a DNP3 client, or the ``Holding Registers`` page of a Modbus client.

A cell can have the attribute ``enabled="false"``. This means the cell is read-only in the editor, NOT that the setting is disabled. PEAT includes these cells. The ``POU Pin Settings`` page describes the function block the editor makes for the item, so PEAT ignores it.

Item types that PEAT parses, and where the results are in the device data (``extra``):

.. list-table::
   :header-rows: 1

   * - Item (XML tag)
     - Key in ``extra``
     - Notes
   * - ``ProjectInfo``
     - ``ProjectInfo``
     - RTACs in the project and the project description (also :attr:`~peat.data.models.Logic.description`)
   * - ``Device``
     - ``Devices``
     - Device connections (Modbus, DNP3, C37.118, access points, etc.). Settings, plus one key for each other page (e.g. ``binary_inputs``), with the column names as keys. The channels of each PMU of a C37.118 client are under ``pmus``. Tags with a protocol address are also added to ``registers``. Remote IP addresses (not multicast groups), ports, device names and protocols are added to ``related``. Names, aliases, comments and other identifier columns are kept as text, other values are converted to numbers and booleans.
   * - ``GooseDevice``
     - ``GooseDevices``
     - IEC 61850 GOOSE subscriptions (``GooseRx``) and publications (``GooseTx``). The GOOSE control block is under ``Message``. The IED names are added to ``related.hosts``.
   * - ``TagList``
     - ``TagLists``
     - Virtual tag lists and C37.118 data streams
   * - ``TagProcessor``
     - ``TagProcessor``
     - Rows are keyed by ``SolveOrder_<n>``
   * - ``ContactIO``, ``SystemTags``, ``SystemTimeControl``, ``MainController``

   * - ``UserLibrary``

     - Name, company, version and parameters
   * - ``RTACBackupableObject``

   * - ``IEC61850Info``

   * - ``Visualization``, ``VisualizationManager``

The models and schema versions of all of the files are in ``extra.ExportSource``. If a file can't be parsed, PEAT logs an error, adds the file name to ``extra.parse_errors``, and continues with the other files.

PEAT uses the same protocol names as for relays in ``related.protocols`` and in ``registers``: for example ``modbus``, ``dnp3``, ``c37.118``, and ``iec61850`` (for GOOSE and MMS).

Limitations:

- A project can have more than one RTAC, with one folder for each RTAC. PEAT parses an export as one device, so items with the same name in different RTACs overwrite each other, and PEAT logs a warning. Parse the folder of each RTAC on its own to keep the data separate.
- The IP address, MAC address and host name of the first Ethernet interface in ``Ethernet Settings.xml`` become the address of the parsed device (the same as for Rockwell L5X project files). Two exports of RTACs with the same configured address (e.g. a factory default) are then merged into one device in the results.
- POUs that only have ``<ArchivedContent>`` are not converted to code.

The test data for RTAC parsing is in ``tests/modules/sel/data_files/rtac/``. It has six public, openly licensed project exports (SEL-3530, SEL-3530-4 and SEL-3555, schemas 22 to 36). ``SOURCES.md`` in that directory has the source and license of each export.

.. _sel-rtac-tls-certificate:

RTAC TLS certificate
^^^^^^^^^^^^^^^^^^^^
The web interface of an RTAC uses HTTPS (HTTP on TCP port 80 redirects to port 443). Unless the owner installs their own certificate, the RTAC uses its factory-default certificate: a self-signed certificate with SEL as the organization and a Common Name like ``SEL-3530-4 RTAC``. Clients can't check such a certificate against a certificate authority, so they can't tell the real RTAC from an impostor unless they trust (pin) that exact certificate. Finding the factory-default certificate on a production RTAC is useful for defenders.

PEAT gets the certificate with :func:`~peat.protocols.tls.fetch_peer_certificate`, which does one TLS handshake and closes the connection. It doesn't log in, send any HTTP requests, or verify the certificate. If the handshake fails with the default TLS settings (TLS 1.2 or newer), PEAT tries once more with a "legacy" TLS context that allows TLS 1.0 and 1.1 and weak ciphers, for older firmware. The certificate is parsed with the ``cryptography`` library (:func:`~peat.protocols.tls.parse_der_certificate`). If ``cryptography`` rejects it (it's stricter than OpenSSL, e.g. about invalid dates), PEAT parses it with the OpenSSL decoder of Python's ``ssl`` module instead, which only gives the names, serial number, version, validity dates and alternative names, and logs a warning.

- During a scan, the ``SEL RTAC SSL certificate`` identification method gets the certificate. The device is an RTAC if the Common Name contains ``SEL`` and ``RTAC``.
- During a pull, PEAT gets the certificate if the scan didn't, e.g. with ``--skip-scan``, or if the RTAC was identified by logging in to the web interface. Set the ``sel.pull_ssl_cert`` option to ``false`` to disable this.

Where the results are:

- ``x509``: the subject and issuer (including the distinguished names), validity dates, serial number, key algorithm and size, signature algorithm (e.g. ``SHA256-RSA``), and the subject alternative names. ``x509.hash`` is the hash of the certificate in PEM format, the same as in other PEAT modules.
- ``extra.ssl_certificate``:

  - ``fingerprints``: ``md5``, ``sha1`` and ``sha256`` are the hashes of the DER-encoded certificate. These are the fingerprints that browsers, ``openssl x509 -fingerprint``, Zeek, and Shodan show. ``spki_sha256`` is the SHA-256 hash of the public key (SubjectPublicKeyInfo), which is the same for every certificate made with the same key, so RTACs with the same ``spki_sha256`` share a key pair. The fingerprints are also added to ``related.hash``.
  - ``default_sel_certificate``: if the certificate looks like the factory default. It's self-signed, the organization is ``Schweitzer Engineering Laboratories, Inc.``, the organizational unit is ``Automation and Integration Engineering``, and the Common Name is ``SEL-<model> RTAC``.
  - ``self_signed``, ``ca`` (from the ``basicConstraints`` extension), ``expired``, ``not_yet_valid``, and ``days_remaining`` (days until the certificate expires, negative if it expired).
  - ``tls_version``, ``cipher``, ``legacy_tls`` (if the legacy TLS context was needed), and ``port``.
  - ``parser``: ``cryptography``, or ``openssl`` if the certificate could only be parsed by OpenSSL. With ``openssl``, there's no ``spki_sha256``, and ``self_signed`` only means that the issuer is the same as the subject.
  - ``chain``: the subject, issuer and SHA-256 fingerprint of each certificate, if the RTAC sent more than one (only with Python 3.13 and newer).

- The ``https`` service has ``tls_version``, ``tls_cipher``, ``tls_legacy``, ``certificate_sha256`` and ``certificate_spki_sha256`` in its ``extra``.
- The model, from a Common Name like ``SEL-3530-4 RTAC`` (the model ``3530-4``), if the model is unknown or less specific (e.g. ``3530``). This doesn't need the factory-default certificate.
- ``ssl-certificate.pem`` in the device's output directory, and ``ssl-certificate-chain.pem`` if the RTAC sent more than one certificate.

To compare a fingerprint with the certificate of an RTAC without PEAT:

.. code-block:: bash

   openssl s_client -connect 192.0.2.20:443 < /dev/null | openssl x509 -noout -fingerprint -sha256

The test data is the factory-default certificate of a SEL-3530-4 (``tests/protocols/data_files/sel_3530_certificate.cert``).

RTAC file hashes
^^^^^^^^^^^^^^^^
The files that the RTAC pull downloads or writes, and the files in a parsed project export tarball, are hashed and added to ``files`` (and the hashes to ``related.hash``). The hashes are calculated from the data in memory, so the files are recorded even if file output is disabled. ``local_path`` is only set to a file that has the same contents as the data that was hashed.

.. list-table::
   :header-rows: 1

   * - Files
     - ``extra.source``
     - ``extra.transport``
   * - Files in the file repository of the web interface (``download.sel``)
     - ``web_download``
     - ``http`` or ``https``
   * - ``raw-pulled-postgres-config.txt`` and ``pulled-postgres-config.json`` (tables read from the PostgreSQL database)
     - ``command_output``
     - ``postgres``
   * - ``ssl-certificate.pem`` and ``ssl-certificate-chain.pem``
     - ``tls_certificate``
     - ``tls``
   * - ``pulled-web-config.json`` and ``logic.st`` (made by PEAT)
     - ``derived``
     -
   * - ``extracted_files/<member>`` (files in a parsed tarball)
     - ``parse_input``
     -

Repository files also have ``extra.listed_size``, the size in the file listing of the web interface, and their modification time from the listing. Files in a tarball have ``extra.archive`` (the name of the tarball), their path in the tarball as the ``path``, and their modification time from the tarball (if it is set and valid).

The hashes of repository files are of the bytes the RTAC sent. The web pages and the Sequence of Events log (``soe.csv``) that are saved to ``http_files/`` are not hashed by the RTAC module.

.. _sel-rtac-engineering-access:

RTAC engineering access discovery
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
An RTAC can be a gateway for engineering access to the IEDs it communicates with: an engineer connects to a port on the RTAC, and the RTAC connects them to a relay on one of its serial or Ethernet connections. PEAT finds these paths in the configuration of the RTAC, in a project export (``peat parse``) and in the PostgreSQL database (``peat pull``). This only reads the configuration. PEAT doesn't connect through the paths it finds.

ACSELERATOR RTAC has two ways to configure engineering access (the names of the settings are from SEL's documentation, HD2014-34 "SEL-3530 RTAC Hands-On Session" and LWP0018-01 "Leveraging Security - Using the SEL RTAC's Built-In Security Features"):

- **Access points and access point routers.** An access point is a port that the RTAC listens on, with a ``Network Connection Type`` (e.g. Telnet, Raw TCP or SSH) and a ``Local Port Number``. An access point router connects an access point to the access point of a device. Each SEL device has two of these: ``<Device>_<Protocol>_TAP`` is a transparent connection, which the RTAC interleaves with its own polling of the device, and ``<Device>_<Protocol>_AP`` is a direct transparent connection. A direct connection stops the RTAC's polling of the device while it's open, so the SCADA data from that device stops.
- **SEL server.** A SEL protocol server with the connection type ``Server - Ethernet Tunneled Serial`` (firmware R134 and newer) listens on one TCP port, the ``Server IP Port``, with a ``Serial Tunneling Mode`` (Telnet, Raw TCP, SSL/TLS or SSH). The client logs in to the RTAC if ``Perform Authentication`` is set (always with SSH). At the RTAC's ``*`` prompt, ``ACC`` goes to access level 1 (the ``*>`` prompt), ``WHO`` lists the SEL devices and their port numbers, and ``PORT <n>`` opens a transparent connection to one of them, if ``Enable Port Command`` is set. The number is the serial port number of a serial device, or the ``Virtual Port Number`` of an Ethernet device. The ``Termination String`` (``<CTRL-D>`` by default) ends the connection.

Where PEAT finds them:

- In a project export, access points are ``Device`` items with the protocol ``AccessPointServer``, and access point routers are ``AccessPointRouter`` items. SEL servers are ``Device`` items with a SEL protocol and ``server`` in the protocol or connection type. A SEL server without a ``Serial Tunneling Mode`` (e.g. for an HMI) only gets a service, since it isn't for engineering access. Other ``Device`` items with a SEL protocol are SEL devices, which a SEL server can reach. The access point of a router is the endpoint that is an access point, whether it's the ``Source`` or the ``Destination``. A destination is matched to a device by its name with or without the ``_TAP`` or ``_AP`` suffix and the protocol (``Feeder_1_SEL_TAP`` is the device ``Feeder_1``), also if the export has the access points of the devices as ``Device`` items. Its route is ``interleaved`` for ``_TAP`` (or the type ``TAP``) and ``direct`` for ``_AP`` (or the type ``AP``). The route to an access point of the RTAC (e.g. on a serial port) isn't known.
- In the database, PEAT uses the tables in :data:`~peat.modules.sel.rtac_engineering_access.PG_TABLES` (``access_points``, ``access_point_ethernet_settings``, ``access_point_routers``, the ``sel_server_*`` and ``sel_client_*`` tables, ``sel_virtual_ports``, ``serial_ports``, ``local_tcp_network_ports``, ``connections``, ``remote_devices`` and others), which the pull already reads. The column names of these tables are not public. PEAT matches the columns to the setting names without regard to case and punctuation (``local_port_number`` matches ``Local Port Number``), and joins the rows of related tables by their ID columns (e.g. ``connection_id`` or ``access_point_id``): two rows are joined if they have the same value in one of these columns, and no different values in the others. Each access point, SEL server and SEL device has a row in one of the tables of its kind. The serial port tables only add the serial port of a SEL device, and the ``local_tcp_network_port*`` tables only add the TCP port of an access point or SEL server, since these tables also have rows for other devices and servers. If a column has a number where PEAT expects a name (e.g. the ID of a tunneling mode), PEAT logs a warning with the column names of the row. PEAT uses every row of these tables, including rows that have the same value in the first column (``pulled-postgres-config.json`` keys the rows by their first column, so only the last of these rows is in that file).

Where the results are:

- ``extra.engineering_access``: one entry for each path to a device. The values can be ``null``.

  .. list-table::
     :header-rows: 1

     * - Key
       - Value
     * - ``name``
       - The destination as configured in the access point router (e.g. ``Feeder_1_SEL_TAP``), or the name of the SEL server
     * - ``rtac_ip``
       - IP address of the RTAC (for a project export, the address of the first Ethernet interface)
     * - ``tcp_port``
       - TCP port on the RTAC
     * - ``transport``
       - ``telnet``, ``raw`` (raw TCP), ``ssh`` or ``tls``
     * - ``kind``
       - ``access_point`` (the port connects to the device) or ``sel_server`` (``PORT <sel_port>`` connects to the device)
     * - ``sel_port``
       - The number for the ``PORT`` command of a SEL server
     * - ``device_name``
       - Name of the device in the RTAC configuration
     * - ``route``
       - ``interleaved`` (``_TAP``, and SEL servers), ``direct`` (``_AP``), or ``null`` if unknown
     * - ``needs_rtac_login``
       - If the configuration requires a login to the RTAC first (SSH, or ``Perform Authentication``). The RTAC may still ask for a login on other access points.
     * - ``termination_string``
       - The characters that end a SEL server session (``"\u0004"`` for ``<CTRL-D>``)
     * - ``source``
       - ``export`` or ``postgres``

  A SEL server has one entry for each SEL device in the configuration, or one entry without a ``sel_port`` if there are none (``WHO`` lists them). A SEL server without the ``PORT`` command, an access point without a router, and UDP access points have no entries.

- ``service``: a service for the port of each access point and SEL server, with the ``configured_port``, the protocol (``telnet``, ``ssh`` or ``tls``, and none for raw TCP, UDP and unknown types), and the role ``engineering_access`` if it reaches any devices (``access_point`` or ``sel_server`` if it doesn't). The ``extra`` of the service has the name, the configured connection type or tunneling mode, the ``destinations`` (with the router, route and SEL port of each), and the security settings of a SEL server: ``perform_authentication``, ``allow_anonymous_clients``, ``allowed_client_ips``, ``disable_remote_access``, ``verify_ssl_certificate``, ``enable_file_transfer_monitor``, the termination string and the timeouts. The ports are also added to ``related.ports``.
- ``extra.engineering_access_devices``: names of the RTAC's own engineering access objects, e.g. ``Eng_Access_40`` in the ``remote_devices`` table. These are not hosts, so they are not added to ``related.hosts``.

:meth:`SELRTAC.downstream_targets() <peat.modules.sel.sel_rtac.SELRTAC.downstream_targets>` returns the entries that have an RTAC IP address and a port, for code that pulls the devices behind a gateway. A path that's in both a project export and the database (the same port, transport, kind, SEL port, device and route) is only once in the results. Other modules that front other devices can have a method with the same name and results. The results include direct routes and routes that aren't known, so code that connects to them must check the ``route``.

For defenders, these are the ways to reach the relays through the RTAC. Paths that don't need the RTAC login, direct routes, Telnet and raw TCP transports, and SEL servers that allow anonymous clients are worth a review.

**TLS certificates and SSH host keys of the ports (opt-in)**

Set the ``sel.rtac_probe_tunnel_ports`` option to ``true`` (it's ``false`` by default) for the pull to connect to each engineering access port that uses TLS or SSH, and get its TLS certificate or SSH host key. The TLS servers of an RTAC normally use the same (activated) certificate as the web interface, and ``same_as_web_certificate`` shows if a port does. PEAT does one TLS handshake (two if it needs the legacy TLS context, refer to :ref:`sel-rtac-tls-certificate`) or one SSH key exchange for each port, then closes the connection. It doesn't log in, send any data, or open a connection to a device, but the RTAC may log the connections. Only the ports of SEL servers (which need the ``PORT`` command to connect to a device) and ports whose routes are all ``interleaved`` are probed. Ports with a direct route, or with a route that isn't known (which may be direct), are never probed, because an access point router may connect to the device as soon as a client connects, and on a direct route that stops the RTAC's polling of the device.

- ``extra.engineering_access_probes``, keyed by ``tcp/<port>``. For TLS: ``tls_version``, ``cipher``, ``legacy_tls``, ``subject``, ``issuer``, ``not_after``, ``fingerprints`` (DER and SPKI, as in ``extra.ssl_certificate``), ``self_signed``, ``default_sel_certificate``, ``same_as_web_certificate`` (``null`` if the web certificate wasn't collected), ``expired``, ``not_yet_valid`` and ``days_remaining``. For SSH: ``key_type``, ``bits``, ``fingerprint`` (``SHA256:...``, as shown by ``ssh-keygen -l``), ``md5``, ``sha256`` (hex) and ``banner``.
- TLS certificates are saved to ``engineering-access-tcp-<port>-certificate.pem`` (and added to ``files``). SSH host keys are added to ``ssh_keys``. The fingerprints are added to ``related.hash``, and to the ``extra`` of the service of the port, which gets the status ``verified``.

Limitations:

- No public export or database dump with engineering access was available, so the test data (``tests/modules/sel/data_files/rtac/synthetic-engineering-access/``) is synthetic, based on SEL's documentation and the format of the public exports. The protocol names of SEL devices and SEL servers in exports, the layout of access point routers, where a serial SEL device has its serial port number, and the column names of the database tables need to be checked with a real RTAC.
- ``Enable_Legacy_Port_Command`` and ``Legacy_Port_Command_ID`` of an access point router are recorded in the ``destinations`` of the service, but PEAT doesn't know what they change.

Developer notes on SEL communications
-------------------------------------
SEL relays can communicate over Telnet, serial connection (e.g. RS-232), or a "engineering tunnel" through a SEL 3530 RTAC (I'm not aware of any relays that support SSH yet, but there might be some newer ones that do). The messages sent are part of what they call "SEL ASCII" commands, and those commands are transport-agnostic, which means the "id" command sent over Telnet will have the same response as one sent over serial or an engineering tunnel. The commands and responses are basic ASCII text, except in certain cases, where it's "Compressed ASCII" (this is rare).

In addition to "SEL ASCII" interfaces, relays also typically have :term:`FTP` and a web interface (using :term:`HTTP` and/or HTTPS), dependent on the configuration. FTP is typically disabled by default, but can be enabled. Since files can be transferred over "ASCII" or FTP, and the commands are very similar, the file transfer code has been generalized in ``peat/modules/sel/sel_comms.py``.

In PEAT, the "SEL ASCII" commands are implemented as a transport-agnostic class, :class:`~peat.modules.sel.sel_ascii.SELAscii`. The sub-classes for specific transports are :class:`~peat.modules.sel.sel_telnet.SELTelnet` and :class:`~peat.modules.sel.sel_serial.SELSerial`. We don't have support for engineering tunnels through an RTAC (yet). The code for scraping and parsing web pages is implemented by :class:`~peat.modules.sel.sel_http.SELHTTP`. Some of the web pages literally run ASCII interface commands internally and just display the results, while other pages pull data in other ways, so there is some overlap in parsing functionality between :class:`~peat.modules.sel.sel_http.SELHTTP` and :class:`~peat.modules.sel.sel_ascii.SELAscii`. The :term:`FTP` interface isn't terribly special, except for a few quirks. The FTP functionality is implemented in ``peat/modules/sel/sel_comms.py`` with functions that call PEAT's generic :class:`~peat.protocols.ftp.FTP` class and handle a few quirks (like changing directories on older relays).

The code gets called from :class:`~peat.modules.sel.sel_relay.SELRelay` class, in the various ``pull_*`` and ``_verify_*`` methods. The ``pull_*`` methods get called by ``pull_project``, which is the function that gets called by PEAT when ``peat pull`` happens, and is defined in the :class:`~peat.device.Device` base class.

YMODEM notes
^^^^^^^^^^^^

YMODEM is required for relays that don't have the ``file show`` command. PySerial doesn't support YMODEM, and the Python ``modem`` package hasn't been updated in over 11 years, so we're forced to subprocess and call the ``rz`` / ``sz`` commands from the ``lrzsz`` project. This is not available on Windows, but is available on Linux (``sudo apt install lrzsz``) and MacOS (``sudo brew install lrzsz``).

- ``show`` supported: 700G, 351S, 351
- ``read``: 451, 2032 (Requires Ymodem to transfer the file)


Things that don't require YMODEM and use ``fil show``

- 351S doesn't require YMODEM and uses ``fil show``.
- 351S was tested on peat rack (port F, front serial, 9600 baud)
- 351 on peat rack tested (port F, front serial, 57600 baud)
- 700G on peat rack tested (port 3, rear serial, 9600 baud)
- 751 should work with ``fil show`` according to the documentation.
- 710 should also work according to the docs
- 311C-1 has ``file show``, according to docs.

Things that DO require YMODEM for file transfer

- 451: DOES require YMODEM for file transfer. It uses ``fil read <file>`` instead of ``fil show``.
- 451: YMODEM with "file read".
- 487E: YMODEM with "file read".
- 2030 (and 2032?): YMODEM with "file read".

XMODEM devices

- 300G. According to docs it doesn't have any "fil" commands, and also requires XMODEM for transfers.
- 311A. Same as above, according to docs.
- 311L-0-6. Same as above.
- 311L-1-7. Same as above.

Telnet notes
^^^^^^^^^^^^

Full list of Telnet commands is in the instruction manual.

From the docs:

   "A command transmitted to the relay consists of the command followed by
   either a CR (carriage return) or a CRLF (carriage return and line feed). You
   can truncate commands to the first three characters. For example, EVENT 1
   <Enter> becomes EVE 1 <Enter>. Use upper- and lowercase characters
   without distinction, except in passwords.

   Each message begins with the start-of-transmission character (ASCII 02) and
   ends with the end-of-transmission character (ASCII 03). Each line of the
   message ends with a carriage return and line feed."
